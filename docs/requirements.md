# Requirements: Travel Journal ไทย (unlock-map app)

## บริบท
แอปมือถือส่วนตัวสำหรับบันทึกการเดินทางในประเทศไทย ผู้ใช้ปักหมุดจังหวัดที่เคยไปเยือนบนแผนที่ 3 มิติแบบเกมมิฟิเคชันที่ "ปลดล็อก" ทีละจังหวัดเมื่อมีการบันทึกทริป ขอบเขต v1 ครอบคลุมเฉพาะ 76 จังหวัดของไทย (ไม่รวมบึงกาฬ เนื่องจากไม่มีในชุดข้อมูลต้นทาง) ไม่มี backend/sync ในรอบนี้ ข้อมูลทั้งหมดเก็บในเครื่องผู้ใช้เท่านั้น

## สมมติฐาน (ถ้ามี)
- สมมติฐาน: มีผู้ใช้เพียงคนเดียวต่อเครื่อง (single-user, local-only) ไม่มีระบบ login/บัญชีใน v1
- สมมติฐาน: "ปลดล็อกจังหวัด" อ้างอิงจากจำนวน journal entry ของจังหวัดนั้น (isVisited = entries.length > 0) ตามที่ระบุใน data model ไม่มีเงื่อนไขอื่นเพิ่ม (เช่น ไม่ต้องยืนยันตำแหน่ง GPS จริง)
- สมมติฐาน: จังหวัดบึงกาฬจะไม่ปรากฏในแอปเลย (ไม่ใช่ทั้ง "76/76 เต็ม" และไม่ใช่ "locked ค้างตลอดไป") — ตัวเลขความคืบหน้าอ้างอิงจาก 76 จังหวัดเป็นฐาน 100%
- สมมติฐาน: รูปภาพที่แนบ (photoUris) เก็บเป็น local URI ผ่าน expo-image-picker เท่านั้น ไม่มีการอัปโหลด/บีบอัดขึ้น cloud ใน v1
- สมมติฐาน: การลบ/แก้ไข journal entry เป็นความสามารถที่ควรมีเพื่อความสมบูรณ์ของฟีเจอร์ แม้โจทย์ต้นฉบับไม่ได้ระบุ UI โดยตรง เพราะจำเป็นต่อการแก้ไขข้อมูลผิดพลาด และมีผลต่อสถานะ unlock (ถ้าลบ entry สุดท้ายของจังหวัด จังหวัดนั้นต้อง lock กลับ)
- สมมติฐาน: ไม่มีข้อจำกัดเรื่องจำนวนรูปสูงสุดต่อ entry หรือขนาดไฟล์ใน v1 (ปล่อยตาม default ของ expo-image-picker)
- สมมติฐาน: แอปทำงาน offline-first ทั้งหมด ไม่ต้องพิจารณาเครือข่ายเลย เพราะไม่มี backend

### สมมติฐานเพิ่มเติม (รอบ Landmark Check-in & Supabase Integration)
- สมมติฐาน: ข้อมูล Landmark (ชื่อ, รายละเอียด, พิกัด/รูปประกอบถ้ามี) มาจาก **static seed dataset ใหม่** ที่ทีมพัฒนาสร้างขึ้นเอง (เช่น `thailand-landmarks.ts`) แพ็กมากับตัวแอป ไม่ใช่ดึงจาก API ภายนอกหรือ user-generated content ในรอบนี้ และปัจจุบันในโค้ดยังไม่มีชุดข้อมูลนี้อยู่เลย (มีแต่ `thailand-provinces.ts` ระดับจังหวัด)
- สมมติฐาน: **การคัดสรร (curate) รายชื่อ Landmark จริง 3–5 แห่งให้ครบทั้ง 76 จังหวัด ถือเป็นงาน content/data ที่ต้องทำแยกต่างหาก** (ไม่ใช่แค่เขียนโค้ด) — ในรอบแรกอาจเริ่มจากจังหวัดนำร่องบางส่วนก่อน แล้วทยอยเพิ่มให้ครบ ทีม PM/Content ต้องวางแผนแหล่งข้อมูลและกระบวนการตรวจสอบความถูกต้องแยกจาก sprint พัฒนาโค้ด
  > **อัปเดต (รอบ OSM Data Integration):** สมมติฐานข้อนี้ถูกแทนที่บางส่วนแล้ว — การคัดสรร Landmark ครบ 76 จังหวัดเปลี่ยนจาก "งาน content ที่ทำด้วยคนล้วนๆ" เป็น "กระบวนการอัตโนมัติผ่าน OSM Overpass API" ตาม US-16 ทีม content/PM ยังคงมีบทบาทในการ manual review เฉพาะจังหวัดที่ข้อมูลไม่พอ (ดูสมมติฐานใหม่ด้านล่าง) ไม่ใช่ curate เองทั้งหมดทีละจังหวัดอีกต่อไป
- สมมติฐาน: ยังไม่มี Supabase project จริงในรอบนี้ ค่า `SUPABASE_URL` และ `SUPABASE_ANON_KEY` จะถูกส่งมาเป็น environment config ภายหลัง การทดสอบ (QA) ของ cloud sync ในรอบนี้จึงจำกัดอยู่ที่การทดสอบ logic กับ Supabase client แบบ mock/local เท่านั้น ยังไม่ใช่การทดสอบกับ production project จริง
- สมมติฐาน: กติกาการจัดการความขัดแย้งของข้อมูล (conflict resolution) เมื่อ entry เดียวกันถูกแก้ไขจากหลายอุปกรณ์ก่อน sync ใช้กติกา **last-write-wins โดยอ้างอิง timestamp การแก้ไขล่าสุด (updated_at)** เป็นค่าเริ่มต้น ยังไม่มี merge หรือแจ้งเตือนผู้ใช้ให้เลือกฝั่งที่จะเก็บ
- สมมติฐาน: ข้อมูล local-only ที่สร้างไว้ก่อนฟีเจอร์นี้ (v1) **ต้องถูก migrate/backfill ขึ้น cloud โดยอัตโนมัติ** เมื่อผู้ใช้ได้บัญชี (ทั้ง anonymous หรือผูก email แล้ว) ไม่ใช่ถูกทิ้งหรือบังคับให้ผู้ใช้กรอกใหม่
- สมมติฐาน: session ของ Anonymous Auth ผูกกับตัวเครื่อง/การติดตั้งแอปครั้งนั้น หากผู้ใช้ **ลบแอปหรือเปลี่ยนเครื่องโดยยังไม่ได้ผูก email ข้อมูลทั้งหมดจะกู้คืนไม่ได้ (unrecoverable)** — นี่คือความเสี่ยงที่ผู้ใช้เผชิญจริง ต้องระบุเป็น AC ที่บังคับให้มี UI แจ้งเตือนความเสี่ยงนี้ (ส่งต่อให้ PM/UIUX ตัดสินใจรูปแบบคำเตือนที่แน่นอน)

### สมมติฐานเพิ่มเติม (รอบ OSM Data Integration)
- สมมติฐาน: เชื่อว่า Overpass API มีข้อมูล tags ที่กำหนด (`tourism=attraction`, `historic=monument|temple`, `amenity=place_of_worship`, `leisure=park`) เพียงพอสำหรับส่วนใหญ่ของ 76 จังหวัด แต่ **ยอมรับว่าบางจังหวัดอาจได้ Landmark น้อยกว่า 3 แห่ง (หรือ 0 แห่ง)** ถ้า OSM ไม่มีข้อมูลครบตามเกณฑ์ในพื้นที่นั้น — จังหวัดที่ได้ไม่ครบ 3 แห่งไม่ถือเป็นความล้มเหลวของระบบ ให้ seed เท่าที่มี (หรือ 0 แห่งแล้วเข้า empty state เดิมของ US-8) และบันทึกไว้เป็นรายการที่ทีม content ต้อง manual review เพิ่มเติมภายหลัง (นอก sprint พัฒนาโค้ดของรอบนี้)
- สมมติฐาน: ขอบเขตพื้นที่ที่ใช้ query Overpass ต่อจังหวัด (bounding box/area) อ้างอิงจากพิกัด centroid ที่มีอยู่แล้วใน `thailand-provinces.ts` ร่วมกับชื่อจังหวัด (ผ่าน Overpass `area["name"="..."]` หรือ bounding box รอบ centroid) ไม่ใช่การวาด/นำเข้าขอบเขตการปกครองระดับจังหวัด (admin boundary polygon) ใหม่ทั้งหมด
- สมมติฐาน: การเก็บพิกัด (lat/lng) ของ Landmark ในรอบนี้ใช้เพื่อ (1) แสดงตำแหน่งตาม US-18 และ (2) เป็น metadata สำหรับต่อยอดในอนาคต (เช่นคำนวณระยะทาง) เท่านั้น **ไม่รวมการแสดงแผนที่แบบเลื่อนดู/ซูมเต็มรูปแบบ (interactive full map) หรือการนำทาง (navigation/turn-by-turn)** ซึ่งยังอยู่นอกขอบเขต
- สมมติฐาน: ผลลัพธ์สถานที่จาก Nominatim ที่ผู้ใช้เลือกในหน้า AddEntryScreen (US-19) จะถูก **prefill เข้าฟิลด์ "ชื่อสถานที่" (title)** ของฟอร์มเพิ่มบันทึกเดิม (US-4) พร้อมแนบพิกัด lat/lng ของผลลัพธ์นั้นเป็น metadata เสริมบน entry record — **ไม่ใช่การสร้าง Landmark ใหม่ในตาราง `landmarks`/seed dataset และไม่ trigger auto check-in ตาม US-10** เพราะเป็นสถานที่ที่ยังไม่ผ่านการคัดกรองเป็น Top Landmark ผู้ใช้ยังคงแก้ไขค่าที่ prefill มาได้เองก่อนบันทึก
- สมมติฐาน: ค่า custom `User-Agent` header ที่ต้องส่งไปกับทุก request ของ Nominatim (ตาม OSM Usage Policy) เป็นค่าคงที่ที่ทีม dev กำหนดเอง (เช่นชื่อแอป + ช่องทางติดต่อ) ไม่ใช่ค่าที่ผู้ใช้ตั้งเองได้ และไม่ใช่ personal data ของผู้ใช้แอป
- สมมติฐาน: การออกแบบตาราง `landmarks` บน Supabase ในรอบนี้เป็นการ **ออกแบบ schema + เขียน seed/sync logic ที่ทดสอบผ่าน mocked/local Supabase client เท่านั้น** สอดคล้องกับแนวทางเดิมของ US-12/US-13 (ยังไม่มี production Supabase project จริงให้เชื่อมต่อ)

### สมมติฐานเพิ่มเติม (รอบ Landmark Cards & Media Integration)
> **หมายเหตุ**: รอบนี้เกิดขึ้นแบบย้อนหลัง (retroactive) — ทีมได้ implement โค้ดไปแล้วก่อนเขียนเอกสารนี้ BA จึงเขียน requirements ให้ตรงกับพฤติกรรมที่ตั้งใจไว้ตามโจทย์ดิบที่ได้รับ เพื่อให้ Tester/QA ใช้ตรวจสอบย้อนกลับว่า implementation ตรงตาม AC หรือไม่ ไม่ใช่การออกแบบ requirement ก่อนเขียนโค้ดตามลำดับปกติของ pipeline
- สมมติฐาน: Wikipedia/Wikimedia Commons เป็น**แหล่งข้อมูลเสริม**ที่ทำงาน**ควบคู่กับ local seed dataset เดิม (`thailand-landmarks.ts`, มาจาก US-8/US-16/US-17)** ไม่ใช่การแทนที่ — Landmark ที่มาจาก Wikipedia (id ขึ้นต้นด้วย `wiki-`) เป็นข้อมูลเสริมที่แสดงผล**ควบคู่กัน**ในหน้าจังหวัด ไม่ทับ/ลบ Landmark เดิมที่มี `id` คงที่ซึ่งผูกกับสถานะเช็คอินของผู้ใช้ (`CheckinContext`) อยู่แล้ว
- สมมติฐาน: Landmark ที่มาจาก Wikipedia (dynamic, id ไม่คงที่ข้าม session เพราะขึ้นกับผลการ query) **เช็คอินได้เช่นเดียวกับ Landmark ที่ curate ไว้ล่วงหน้า** โดยใช้ `id` เดียวกันที่ generate ตอน fetch (`wiki-{provinceId}-{slug}`) เป็น key ผูกกับ `CheckinContext` เดิม — ยอมรับความเสี่ยงว่าถ้า Wikipedia เปลี่ยนชื่อบทความ/ผลลัพธ์เปลี่ยนไป slug อาจเปลี่ยนและสถานะเช็คอินเดิมของ Landmark ตัวนั้นอาจหลุด (ต่างจาก Landmark จาก seed dataset ที่ id ตายตัว) — เป็นความเสี่ยงที่ยอมรับได้ในรอบนี้ ไม่ต้องมี migration/reconciliation พิเศษ
- สมมติฐาน: การเรียก Wikipedia/Wikimedia Commons API เป็น runtime fetch (ไม่ใช่ build-time เหมือน Overpass ของ US-16) เพราะเนื้อหา/รูปภาพอาจอัปเดตได้ และไม่ต้องการ pre-bundle ข้อมูลจำนวนมากเข้าแอป — หมายความว่าฟีเจอร์นี้**ต้องมีเน็ตถึงจะเห็นการ์ด Wikipedia ได้** ถ้าไม่มีเน็ต/API ล้มเหลว ต้อง fallback แสดงเฉพาะ Landmark จาก local seed dataset เดิม (ไม่ error, ไม่ค้าง)
- สมมติฐาน: ไม่มี API key/authentication สำหรับ MediaWiki API (เป็น public API ฟรี) จึงไม่มี rate-limit quota ที่ทีมควบคุมได้โดยตรง แต่ยังต้องแนบ custom `User-Agent` header ตาม Wikimedia API etiquette เช่นเดียวกับที่ทำกับ Nominatim ใน US-19/US-20 และต้อง cache ผลลัพธ์ระดับ in-memory ต่อจังหวัดระหว่างเปิดแอปเพื่อลดจำนวน request ซ้ำ (ไม่ต้อง persist cache ข้าม session ในรอบนี้)
- สมมติฐาน: การแปลงรูปเป็น JPEG (แก้ปัญหา HEIC) เกิดขึ้น**ทันทีที่เลือกรูปจากแกลเลอรี** (ก่อนบันทึก entry) ไม่ใช่ตอน sync/upload — ถ้าการแปลงล้มเหลว (`expo-image-manipulator` throw) ให้ fallback ใช้ URI ต้นฉบับต่อไม่ block ผู้ใช้จากการเพิ่มรูป (ยอมรับว่ารูปนั้นอาจยังแสดงผลผิดปกติถ้าเป็น HEIC ต้นฉบับจริงๆ)
- สมมติฐาน: Global search (ค้นหาทั่วประเทศบนแผนที่ 3D) ค้นหาเฉพาะข้อมูลที่มีอยู่ใน local dataset ที่โหลดมาแล้ว (`thailand-provinces.ts` + `thailand-landmarks.ts` ที่ curate ไว้ล่วงหน้า) **ไม่ได้ยิง Wikipedia API สดๆ ตอนพิมพ์ค้นหา** — จึงทำงาน offline ได้เต็มรูปแบบสำหรับการค้นหาจังหวัด/landmark ที่ curate ไว้แล้ว แต่จะไม่เจอสถานที่ที่มีเฉพาะบน Wikipedia ที่ยังไม่เคยถูก fetch เข้ามาในจังหวัดนั้น

### สมมติฐานเพิ่มเติม (รอบ Bug Fix: Landmark Loading Error Visibility)
- สมมติฐาน: "ดึงข้อมูลล้มเหลว" หมายถึงกรณีที่ `fetchAttractionsForProvince` (ใน `wikipediaService.ts`) throw exception หรือ promise reject จริง (เช่น network error, HTTP error, timeout, JSON parse error) เท่านั้น ส่วนกรณีที่ query สำเร็จแต่ไม่มีบทความ Wikipedia อยู่ในหมวดหมู่ของจังหวัดนั้นจริงๆ (resolve เป็น array ว่างโดยไม่มี exception) ถือเป็น "ไม่มีข้อมูล" ตามปกติ ไม่ใช่ error — เป็นเกณฑ์ที่ใช้แบ่งแยกสองเคสตาม US-25
- สมมติฐาน: รอบนี้แก้เฉพาะกลไกการแยกแยะและแสดงผล error/empty state ของ Wikipedia fetch เท่านั้น ไม่รวมการเปลี่ยนแหล่งข้อมูลหรือเพิ่ม curated data ให้ 68 จังหวัดที่เหลือใน `thailand-landmarks.ts` ซึ่งยังคง out of scope ตามสมมติฐานเดิม (รอบ Landmark Check-in & Supabase Integration)

### สมมติฐานเพิ่มเติม (รอบ Bottom Tab Navigation & ข่าวท่องเที่ยว RSS)
> **บริบทการตัดสินใจ**: ผู้ใช้เลือก 2 ประเด็นหลักผ่าน orchestrator แล้ว (1) โครงสร้าง navigation เป็น **Bottom Tab Bar** และ (2) แหล่งข่าวเป็น **RSS จากหน่วยงานจริง** สมมติฐานด้านล่างเป็นรายละเอียดที่ BA ตัดสินใจต่อยอดจาก 2 ข้อนั้นเพื่อให้ implement ได้จริง
- สมมติฐาน: root navigation เปลี่ยนจาก native stack เดี่ยวเป็น **Bottom Tab Navigator ระดับบนสุด 2 แท็บ**: "แผนที่" (HomeScreen เดิม) และ "ข่าว" (NewsScreen ใหม่) แต่ละแท็บมี stack navigator ของตัวเองซ้อนอยู่ข้างใน (nested stack) เพื่อให้ ProvinceDetail/AddEntry ยังคง push ทับจากแท็บ "แผนที่" ได้เหมือนเดิมโดยไม่ต้องออกแบบ flow ใหม่ทั้งหมด
- สมมติฐาน: Stats และ Settings **ยังคงเข้าถึงผ่านปุ่มไอคอนใน header เหมือนเดิม ไม่ทำเป็นแท็บที่ 3** เพื่อลดความซับซ้อนของการเปลี่ยนแปลงในรอบนี้ — ปุ่มไอคอนนี้ปรากฏอยู่ใน header ของทั้ง 2 แท็บ (ไม่ใช่เฉพาะแท็บ "แผนที่" เหมือนก่อนหน้านี้) เพื่อให้ผู้ใช้เข้าถึง Stats/Settings ได้จากทุกที่ในแอปเหมือนพฤติกรรมเดิมที่คุ้นเคย
- สมมติฐาน: RSS source ที่เสนอเป็นตัวเลือกแรกคือ **TAT News (การท่องเที่ยวแห่งประเทศไทย, เสนอ endpoint `https://www.tatnews.org/feed/`)** ซึ่งเป็นเว็บไซต์ข่าวท่องเที่ยวอย่างเป็นทางการที่มักมี RSS feed มาตรฐานแบบ WordPress `/feed/` — อย่างไรก็ตาม **BA ไม่สามารถยืนยัน 100% ว่า URL นี้ยัง active และคืนค่าเป็น valid RSS/Atom XML จริง ณ เวลา implement** จึงกำหนดเป็น requirement ว่าทีม dev **ต้อง verify endpoint จริงก่อนเริ่ม implement** ถ้าใช้ไม่ได้ให้เลือกแหล่งสำรองที่เป็น public RSS จริงของหน่วยงานท่องเที่ยว/สำนักข่าวไทยที่มีหมวดข่าวท่องเที่ยว (เช่นสำนักข่าวใหญ่ที่เปิด RSS สาธารณะ) โดยต้อง log/แจ้งทีมว่าเปลี่ยนมาใช้แหล่งใดแทน
- สมมติฐาน: การ parse RSS/XML ทำแบบ client-side ในตัวแอปเอง (ไม่มี backend/proxy ของทีมแปลงข้อมูลก่อน) โดย field ที่ต้อง parse ต่อข่าวคือ title, summary/description (ตัด HTML tag ออกก่อนแสดงผล), image (จาก `<enclosure>`, `<media:content>` หรือรูปแรกที่ parse ได้จาก description HTML — ถ้าไม่มีเลยใช้ placeholder), link (URL ไปต้นทาง), และวันที่เผยแพร่ (`pubDate`)
- สมมติฐาน: cache ข่าวเป็นแบบ **persist ลง local storage (เช่น AsyncStorage)** ไม่ใช่ in-memory เฉยๆ แบบ Wikipedia cache เดิม (US-22) เพราะโจทย์ระบุชัดเจนว่าต้องการ "offline-friendly" ระยะเวลาก่อน refresh อัตโนมัติ ("cache ไว้เป็นช่วงๆ") เป็นค่าคงที่ที่ทีม dev กำหนด (เสนอ 30–60 นาที) ผู้ใช้สามารถ pull-to-refresh เพื่อบังคับดึงใหม่ได้เสมอไม่ว่าจะครบเวลาหรือไม่
- สมมติฐาน: การเปิดอ่านข่าวเต็มที่ต้นทางใช้ **in-app browser ผ่าน `expo-web-browser` (`openBrowserAsync`)** แทนการเปิดแอปเบราว์เซอร์ภายนอกเต็มรูปแบบ เหตุผล: ผู้ใช้ไม่หลุดออกจากบริบทแอป ปิดแล้วกลับมาที่รายการข่าวได้ทันที ในขณะที่ยังคง "ไม่ทำ full article parsing เอง" เพราะเนื้อหาเต็มยัง render จากเว็บต้นทางจริงผ่าน browser engine ไม่ใช่การ parse/แสดงเองในแอป
- สมมติฐาน: ไม่มีการกรอง/จัดหมวดหมู่ข่าวตามภูมิภาคหรือจังหวัดในรอบนี้ (แสดงข่าวทั้งหมดจาก feed เดียวเรียงตามวันที่เผยแพร่ ไม่ผูกกับจังหวัดที่ปลดล็อกหรือ landmark ที่เช็คอินแล้วแต่อย่างใด)

## User Stories

### US-1: ดูภาพรวมความคืบหน้าบนแผนที่ 3 มิติ
As a ผู้ใช้แอป, I want เห็นแผนที่ 3 มิติของ 76 จังหวัดพร้อมสถานะปลดล็อก/ยังไม่ปลดล็อกในหน้าแรก, so that รู้สึกถึงความคืบหน้าของการเดินทางได้ในทันทีที่เปิดแอป

**Acceptance Criteria:**
- [ ] หน้า home แสดง SVG ของทั้ง 76 จังหวัดจาก `thailand-provinces.ts` ครบทุก province (ไม่มีจังหวัดหาย ไม่มี id ซ้ำ/ไม่ตรงกับ dataset)
- [ ] จังหวัดที่ไม่มี entry ใดๆ แสดงเป็นสถานะ locked (สีเทา, ไม่ยกตัว/ไม่มี side face มองเห็น)
- [ ] จังหวัดที่มี entry อย่างน้อย 1 รายการ แสดงเป็นสถานะ unlocked (top face สีเขียว/เขียวมิ้นท์ยกตัวขึ้น, side face สีเข้มกว่ามองเห็นได้)
- [ ] ส่วนหัวเหนือแผนที่แสดงข้อความ "ปลดล็อกแล้ว X / 76 จังหวัด" พร้อม progress bar ที่ค่า X อัปเดตทันทีเมื่อจำนวนจังหวัดปลดล็อกเปลี่ยน
- [ ] มี legend อธิบายความหมายของสี locked vs unlocked อยู่ใต้แผนที่

### US-2: เปิดดูรายละเอียดจังหวัดจากแผนที่
As a ผู้ใช้แอป, I want แตะที่จังหวัดบนแผนที่แล้วเข้าสู่หน้ารายละเอียดของจังหวัดนั้น, so that ดูหรือเพิ่มบันทึกการเดินทางของจังหวัดนั้นได้

**Acceptance Criteria:**
- [ ] แตะจังหวัดใดๆ (ทั้ง locked และ unlocked) แล้วนำทางไปหน้ารายละเอียดของจังหวัดนั้นถูกต้องตรงกับ province.id ที่แตะ
- [ ] tap target ของแต่ละจังหวัดครอบคลุมพื้นที่ path จริงของจังหวัดนั้น (ไม่ทับซ้อนจนกดผิดจังหวัดข้างเคียงบ่อยผิดปกติ) แม้ในจังหวัดที่มีพื้นที่เล็ก (เช่น สมุทรสงคราม)
- [ ] จังหวัด locked ที่ยังไม่มี entry เมื่อแตะแล้วเข้าหน้ารายละเอียดที่พร้อมให้กดเพิ่มบันทึกแรกได้ทันที (ไม่ใช่ dead-end หรือ error)

### US-3: เล่นอนิเมชันปลดล็อกแบบ 3 มิติเมื่อสถานะเปลี่ยน
As a ผู้ใช้แอป, I want เห็นจังหวัดที่เพิ่งปลดล็อก "ลอยขึ้น" เป็นบล็อกพร้อมอนิเมชันสปริงตอนย้อนกลับมาหน้าแผนที่, so that รู้สึกได้รับรางวัลและเห็นผลลัพธ์ของการบันทึกทริปทันที

**Acceptance Criteria:**
- [ ] เมื่อบันทึก entry แรกของจังหวัดสำเร็จแล้วกลับสู่หน้าแผนที่ จังหวัดนั้นเปลี่ยนจาก flat/เทา เป็น elevated/เขียวด้วยอนิเมชัน spring/bounce (ไม่ใช่เปลี่ยนทันทีแบบไม่มีทรานซิชัน)
- [ ] จังหวัดอื่นที่ปลดล็อกอยู่ก่อนแล้วไม่เล่นอนิเมชันซ้ำเมื่อกลับมาหน้าแผนที่ (เล่นเฉพาะจังหวัดที่เพิ่งเปลี่ยนสถานะ)
- [ ] แผนที่ทั้งหมดอยู่ในกรอบเอียง (rotateX ประมาณ 30–40 องศา) ตลอดเวลา ไม่ใช่เฉพาะตอนอนิเมชัน

### US-4: เพิ่มบันทึกทริปใหม่ให้จังหวัด
As a ผู้ใช้แอป, I want เพิ่มบันทึกทริป (วันที่, ชื่อสถานที่, บันทึกข้อความ, รูปภาพ, แท็ก) ให้จังหวัดที่ไปเยือน, so that เก็บความทรงจำการเดินทางไว้เป็นหลักฐานถาวรในเครื่อง

**Acceptance Criteria:**
- [ ] หน้ารายละเอียดจังหวัดมีปุ่ม "+ เพิ่มบันทึกใหม่" ที่เปิดฟอร์มกรอกข้อมูลครบทุกฟิลด์ตาม data model: date, title, notes, photoUris (อย่างน้อย 0 รูปได้), tags
- [ ] ฟอร์มบังคับกรอกอย่างน้อย title และ date ก่อนบันทึกได้ (แสดง error ถ้าขาด) ส่วน notes/photos/tags เป็น optional
- [ ] ผู้ใช้เลือกรูปได้ผ่าน expo-image-picker และแนบได้มากกว่า 1 รูปต่อ entry
- [ ] บันทึกสำเร็จแล้ว entry ใหม่ถูกเก็บลง local storage (expo-sqlite) ผูกกับ provinceId ที่ถูกต้อง และปิดแอปเปิดใหม่ข้อมูลยังอยู่ครบ
- [ ] ถ้าเป็น entry แรกของจังหวัดนั้น สถานะจังหวัดเปลี่ยนเป็น unlocked ทันทีหลังบันทึก

### US-5: ดูรายการบันทึกทั้งหมดของจังหวัด
As a ผู้ใช้แอป, I want ดูรายการบันทึกทริปทั้งหมดของจังหวัดหนึ่งเรียงจากล่าสุดไปเก่าสุด, so that ทบทวนความทรงจำของแต่ละจังหวัดได้ง่าย

**Acceptance Criteria:**
- [ ] หน้ารายละเอียดจังหวัดแสดงชื่อจังหวัดภาษาไทย (nameTh) เป็นหัวข้อหลัก
- [ ] รายการ entry เรียงจากวันที่ล่าสุดไปเก่าสุด (reverse-chronological ตามฟิลด์ date)
- [ ] แต่ละรายการใน list แสดงอย่างน้อย title, date และ thumbnail รูปแรก (ถ้ามีรูป)
- [ ] จังหวัดที่ไม่มี entry เลยแสดง empty state ที่ชัดเจน พร้อมปุ่ม/ทางเข้าไปสู่การเพิ่ม entry แรก

### US-6: ดูภาพรวมสถิติการเดินทางทั้งหมด
As a ผู้ใช้แอป, I want เห็นหน้าสรุปสถิติ (จำนวนจังหวัดที่ปลดล็อก, จำนวน entry ทั้งหมด, ภาคที่ไปเยือนเยอะที่สุด) และ timeline ของทุกบันทึก, so that เห็นภาพรวมพฤติกรรมการเดินทางของตัวเองทั้งหมด

**Acceptance Criteria:**
- [ ] หน้าสถิติแสดงจำนวนจังหวัดที่ unlocked ทั้งหมด (เทียบกับฐาน 76) และจำนวน journal entry ทั้งหมดที่มีในระบบ ตรงกับข้อมูลจริงใน local storage
- [ ] หน้าสถิติคำนวณและแสดงภาค (north/northeast/central/east/west/south → แปลเป็นชื่อไทยตามที่ระบุ: ภาคเหนือ/อีสาน/กลาง/ตะวันออก/ตะวันตก/ใต้) ที่มีจำนวนจังหวัด unlocked มากที่สุด โดยอ้างอิงฟิลด์ region ของแต่ละจังหวัด
- [ ] มี timeline แสดง entry ทั้งหมดจากทุกจังหวัดเรียงจากล่าสุดไปเก่าสุด แต่ละรายการระบุได้ว่าเป็นของจังหวัดไหน
- [ ] กรณียังไม่มี entry ใดๆ เลยในระบบ หน้าสถิติแสดง empty state ที่เหมาะสม (ไม่ error, ไม่ค่าว่างเปล่าดิบๆ อย่าง NaN หรือ undefined)

### US-7: ตรวจสอบพื้นฐานของแผนที่ 2 มิติก่อนต่อยอด (validation step)
As a ทีมพัฒนา, I want เวอร์ชันเริ่มต้นของแผนที่ที่ render เป็น 2 มิติแบบเรียบ (ไม่มีอนิเมชัน 3 มิติ) พร้อม toggle สถานะ visited ใน memory ชั่วคราว, so that ยืนยันว่าข้อมูล path และ tap target ของทั้ง 76 จังหวัดถูกต้องก่อนลงทุนสร้างความซับซ้อนของอนิเมชัน 3 มิติ

**Acceptance Criteria:**
- [ ] แผนที่ 2 มิติ render ครบทั้ง 76 จังหวัดจาก dataset โดยใช้ path data ตรงจาก `thailand-provinces.ts` โดยไม่มีการแก้ไข/re-derive พิกัด
- [ ] แตะจังหวัดแล้ว toggle สถานะ visited (สีเทา ↔ สีเขียว) ได้ถูกต้องใน state ของ memory เท่านั้น (ยังไม่ต้อง persist หรือผูกกับ journal entry ใดๆ ในขั้นนี้)
- [ ] ขั้นตอนนี้ถือเป็น internal/dev validation step ไม่ใช่หน้าจอที่ end-user เห็นใน production build ของ v1

### US-8: ดูรายการ Landmark แนะนำประจำจังหวัดและเช็คอิน
As a ผู้ใช้แอป, I want เห็นรายการ Landmark เด่น (3–5 แห่ง) ของจังหวัดที่กำลังดูอยู่ และกดเช็คอินเมื่อไปเยือนแล้ว, so that ติดตามได้ว่าเที่ยวครบสถานที่สำคัญของจังหวัดนั้นแค่ไหน

**Acceptance Criteria:**
- [ ] หน้า ProvinceDetailScreen แสดงรายการ Landmark ของจังหวัดนั้นจาก landmark seed dataset (สูงสุด 3–5 รายการต่อจังหวัดตามข้อมูลที่มี) พร้อมชื่อ Landmark อย่างน้อย
- [ ] แต่ละ Landmark มีปุ่ม/สวิตช์ Check-in ที่กดแล้ว toggle สถานะ visited/not-visited ได้ และสถานะที่ toggle แล้ว persist ลง local storage ทันที (ปิดแอปเปิดใหม่สถานะยังอยู่)
- [ ] มี progress indicator แสดงจำนวนที่เช็คอินแล้วเทียบทั้งหมดของจังหวัดนั้น ในรูปแบบ "เช็คอินแล้ว X/Y แห่ง" และค่าตัวเลขอัปเดตทันทีเมื่อ toggle
- [ ] จังหวัดที่ยังไม่มีข้อมูล Landmark ใน seed dataset (เช่นจังหวัดที่ยังไม่ถูก curate ในรอบแรก) แสดง empty state ที่สื่อว่า "ยังไม่มีข้อมูลสถานที่แนะนำ" แทนที่จะ error หรือแสดงพื้นที่ว่างเปล่า

### US-9: ได้รับตราสัญลักษณ์ Province Master เมื่อเช็คอินครบทุก Landmark
As a ผู้ใช้แอป, I want เห็นตราสัญลักษณ์พิเศษเมื่อเช็คอิน Landmark ครบทุกแห่งของจังหวัด, so that รู้สึกถึงความสำเร็จที่ทำภารกิจของจังหวัดนั้นครบถ้วน

**Acceptance Criteria:**
- [ ] เมื่อจำนวน Landmark ที่เช็คอินแล้วเท่ากับจำนวน Landmark ทั้งหมดของจังหวัดนั้น (และมี Landmark อย่างน้อย 1 แห่ง) หน้า ProvinceDetailScreen แสดงตราสัญลักษณ์ "Province Master ⭐" ทันที
- [ ] ถ้าผู้ใช้ยกเลิกเช็คอิน (toggle กลับ) จน Landmark ไม่ครบอีกต่อไป ตราสัญลักษณ์ต้องหายไปทันที (สถานะคำนวณสดจากจำนวนเช็คอินปัจจุบัน ไม่ค้างจากที่เคยได้)
- [ ] จังหวัดที่ยังไม่มีข้อมูล Landmark เลย (0 แห่ง) จะไม่แสดงตราสัญลักษณ์นี้ (ไม่ถือว่า "ครบ" เพราะไม่มีฐานให้เทียบ)

### US-12: ซิงค์ข้อมูลบันทึกทริปและเช็คอิน Landmark ขึ้น Supabase แบบ Offline-First

### US-16: สคริปต์ดึงข้อมูล Top Landmark จาก OSM Overpass API ครบ 76 จังหวัด (one-time/build-time)
As a ทีมพัฒนา/ทีม content, I want สคริปต์ที่รันครั้งเดียวตอน dev/build เพื่อดึงจุดแลนด์มาร์กสำคัญ 3–5 จุดต่อจังหวัด (พร้อมพิกัด lat/lng) จาก OSM Overpass API แล้ว generate เป็นไฟล์ data สำหรับทั้ง 76 จังหวัด, so that ได้ชุดข้อมูล Top Landmark ที่ครอบคลุมทุกจังหวัดโดยไม่ต้องคัดสรรด้วยมือทีละแห่ง และไม่ต้องพึ่ง API ภายนอกตอนแอปทำงานจริง

**Acceptance Criteria:**
- [ ] สคริปต์นี้เป็นเครื่องมือฝั่ง dev/build-time เท่านั้น (เช่นรันผ่าน `node`/CLI แยกต่างหาก) ไม่ถูก import หรือเรียกใช้จากโค้ดฝั่ง runtime ของแอป และไม่ถูก bundle รวมเข้า production app bundle
- [ ] สำหรับแต่ละจังหวัดใน 76 จังหวัดของ `thailand-provinces.ts` สคริปต์ query Overpass API โดย filter เฉพาะ tags: `tourism=attraction`, `historic=monument` หรือ `historic=temple`, `amenity=place_of_worship`, `leisure=park` ภายในพื้นที่ของจังหวัดนั้น แล้วคัดเลือกผลลัพธ์สูงสุด 3–5 แห่งต่อจังหวัดตามลำดับความสำคัญของ tag ที่กำหนดไว้ล่วงหน้า (กติกาการจัดลำดับให้ทีม dev/content เป็นผู้กำหนดรายละเอียด)
- [ ] ทุก Landmark ที่ดึงมาได้ต้องมีพิกัด lat และ lng เป็นตัวเลขที่ถูกต้อง (ไม่ null/NaN) — ถ้ารายการใดจาก Overpass ไม่มีพิกัด ให้ตัดรายการนั้นออกแทนที่จะบันทึกพิกัดว่าง
- [ ] ผลลัพธ์ของสคริปต์ถูกเขียนออกเป็นไฟล์ data ใหม่ที่ขยายจาก schema เดิมของ `thailand-landmarks.ts` (เพิ่มฟิลด์ `lat`/`lng`) โดยยังคงฟิลด์เดิม (`id`, `provinceId`, `nameTh`) ไว้ครบ ไม่ทำให้โค้ด/เทสที่มีอยู่ของ US-8/US-9/US-10 พังเนื่องจาก schema เปลี่ยน
- [ ] จังหวัดใดที่ Overpass คืนผลลัพธ์ตามเกณฑ์น้อยกว่า 3 แห่ง สคริปต์ยังคงบันทึกเท่าที่มี (หรือ 0 แห่ง) และแยกบันทึก/log รายชื่อจังหวัดเหล่านั้นไว้เป็นรายการที่ต้อง manual review เพิ่มเติม แทนที่จะทำให้สคริปต์ทั้งหมด fail หรือใส่ข้อมูลปลอม
- [ ] สคริปต์รองรับกรณี request ต่อจังหวัดล้มเหลว/timeout/โดน rate limit จาก Overpass (เช่น หน่วงเวลาระหว่าง request แต่ละจังหวัด และ retry อย่างน้อย 1 ครั้งก่อนข้าม) โดยความล้มเหลวของจังหวัดหนึ่งต้องไม่ทำให้ผลลัพธ์ของจังหวัดอื่นที่สำเร็จแล้วเสียหายหรือหายไป
- [ ] เมื่อรันจบ สคริปต์สรุปผลให้เห็นชัดเจนว่ามีกี่จังหวัดที่ได้ครบ 3–5 แห่ง, กี่จังหวัดที่ได้ไม่ครบ, และกี่จังหวัดที่ล้มเหลว/ไม่มีข้อมูลเลย

### US-17: รวมข้อมูล Landmark (พร้อมพิกัด) เข้าสู่แอปแบบ Offline และออกแบบตาราง Supabase รองรับ
As a ผู้ใช้แอป, I want ให้แอปมีข้อมูล Top Landmark ของทุกจังหวัดที่มีข้อมูล (พร้อมพิกัด) พร้อมใช้งานได้ทันทีแบบ 100% offline โดยไม่ต้องรอโหลดจากอินเทอร์เน็ต, so that เปิดดู/เช็คอิน Landmark ของจังหวัดใดก็ได้ทันทีเหมือนเดิม แม้ไม่มีเน็ต

**Acceptance Criteria:**
- [ ] ไฟล์ local cache/dataset ของ Landmark ในแอป (เช่น `thailand-landmarks.ts` หรือไฟล์ที่แทนที่) ถูกอัปเดตด้วยผลลัพธ์จากสคริปต์ใน US-16 ครอบคลุมทุกจังหวัดที่มีข้อมูลจาก Overpass (ไม่จำกัดแค่ 8 จังหวัดนำร่องเดิมอีกต่อไป) โดยแต่ละ Landmark มีครบ `id`, `provinceId`, `nameTh`, `lat`, `lng`
- [ ] การอ่านรายการ Landmark ของจังหวัดใดๆ ในแอป (ProvinceDetailScreen ตาม US-8, dropdown ตาม US-10) ยังคงทำงานได้ 100% offline จากไฟล์ local เท่านั้น ไม่มีการเรียก Overpass API หรือ network request ใดๆ ระหว่างการใช้งานปกติของแอป
- [ ] มีการออกแบบตาราง `landmarks` บน Supabase (schema สอดคล้องกับ local dataset: `id`, `province_id`, `name_th`, `lat`, `lng`) พร้อม seed/sync logic สำหรับนำข้อมูลจาก local dataset ขึ้น Supabase เมื่อมีการเชื่อมต่อ โดยทดสอบผ่าน mocked/local Supabase client เท่านั้น (ตาม pattern เดียวกับ US-12/US-13) ยังไม่ใช่การ seed ขึ้น production project จริง
- [ ] จังหวัดที่ไม่มีข้อมูล Landmark เลย (0 แห่ง จาก Overpass และยังไม่ผ่าน manual review) ยังคงแสดง empty state เดิมตาม US-8 ไม่ error และไม่ทำให้จังหวัดอื่นเสียหาย
- [ ] ข้อมูล Landmark เดิมของ 8 จังหวัดนำร่อง (T35) ที่มีอยู่แล้วต้องไม่สูญหายหรือถูก id เปลี่ยน หากมีการ merge ผลลัพธ์ใหม่จาก Overpass เข้ากับจังหวัดเดียวกัน ต้องระบุวิธี reconcile ให้ชัดเจน (เช่น คงของเดิมไว้แล้วเติมเฉพาะพิกัดที่ขาด หรือแทนที่ทั้งชุดตามเกณฑ์ใหม่) โดยไม่ทำให้สถานะ check-in ที่ผู้ใช้เคยบันทึกไว้ (ผูกกับ landmark id เดิม) หายไป

### US-18: เห็นตำแหน่ง Landmark บนแผนที่ระดับจังหวัด
As a ผู้ใช้แอป, I want เห็นตำแหน่งของ Landmark แต่ละแห่งบนแผนที่ในหน้ารายละเอียดจังหวัด, so that รู้ตำแหน่งจริงของสถานที่ก่อนวางแผนไปเยือน

**Acceptance Criteria:**
- [ ] หน้า ProvinceDetailScreen แสดงตำแหน่ง (lat/lng) ของ Landmark แต่ละแห่งที่มีพิกัดครบ เป็นจุด/หมุดบนองค์ประกอบแผนที่ของหน้านั้น (รูปแบบภาพ/การจัดวางที่แน่นอนเป็นหน้าที่ของ UIUX ออกแบบต่อ — requirement นี้กำหนดเฉพาะพฤติกรรมว่าต้องมีและต้องแม่นยำตามพิกัดที่มี)
- [ ] Landmark ที่ไม่มีพิกัด (lat/lng ไม่ครบ เช่นยังไม่ผ่าน US-16/US-17) จะไม่แสดงจุดบนแผนที่ แต่ยังคงปรากฏในรายการ list ปกติตาม US-8 โดยไม่ error และไม่ทำให้ Landmark อื่นที่มีพิกัดหายไปด้วย
- [ ] การแตะ/เลือกจุด Landmark บนแผนที่ (ถ้าถูกออกแบบให้กดได้) ต้องอ้างอิงถึง Landmark เดียวกัน (landmark id เดียวกัน) กับรายการใน list ของ US-8 เสมอ ไม่มีจุดที่ map ผิดตัวหรือชี้ไปยัง Landmark ของจังหวัดอื่น
- [ ] ฟีเจอร์นี้ทำงานได้ 100% offline โดยใช้พิกัดจาก local dataset/cache เดิม (US-17) เท่านั้น ไม่มีการเรียก Overpass หรือบริการแผนที่ภายนอกใดๆ เพื่อแสดงผลจุดเหล่านี้

### US-19: ค้นหาสถานที่ที่ไม่อยู่ใน Top Landmarks ผ่าน OSM Nominatim ตอนเพิ่มบันทึกทริป
As a ผู้ใช้แอป, I want ค้นหาชื่อสถานที่ที่ไม่ได้อยู่ในรายการ Top Landmarks ของจังหวัด ผ่านช่องค้นหาในฟอร์มเพิ่มบันทึกทริป, so that บันทึกทริปที่ไปสถานที่ทั่วไป/ไม่เป็นที่รู้จักได้โดยไม่ต้องพิมพ์ชื่อและพิกัดเอง

**Acceptance Criteria:**
- [ ] หน้า AddEntryScreen มีช่องค้นหาสถานที่แบบ optional เพิ่มเติมจาก field เลือก Landmark เดิม (US-10) สำหรับค้นหาสถานที่ที่ไม่อยู่ใน Top Landmarks ของจังหวัดนั้น โดยไม่บังคับใช้งาน (ไม่กระทบ flow เดิมของ US-4/US-10 ถ้าไม่ใช้)
- [ ] เมื่อผู้ใช้พิมพ์คำค้นและมีเน็ต ระบบยิง request ไปยัง Nominatim (`https://nominatim.openstreetmap.org/search?format=json&countrycodes=th&q=...`) และแสดงรายการผลลัพธ์ที่ได้ในรูปแบบ list ให้เลือก
- [ ] เมื่อผู้ใช้เลือกผลลัพธ์รายการหนึ่ง ระบบ prefill ค่าไปยังฟิลด์ "ชื่อสถานที่" (title) ของฟอร์มเดิมโดยอัตโนมัติ พร้อมเก็บพิกัด lat/lng ของผลลัพธ์นั้นแนบไปกับ entry เป็น metadata เสริม (ผู้ใช้ยังแก้ไขค่าที่ prefill มาได้ก่อนบันทึกจริง)
- [ ] การเลือกผลลัพธ์จาก Nominatim **ไม่ทำให้เกิดการสร้าง Landmark ใหม่ในตาราง/seed dataset และไม่ trigger auto check-in** ตาม US-10 (แยกกลไกจาก dropdown เลือก Landmark ที่ curate ไว้แล้วโดยเด็ดขาด)
- [ ] ผู้ใช้ยังคงบันทึก entry ได้ตามปกติโดยไม่ใช้ช่องค้นหานี้เลย (พิมพ์ title เองตรงๆ) เหมือนพฤติกรรมเดิมของ US-4 ทุกประการ

### US-20: จัดการ Rate Limit, Error และ Offline State ของการค้นหาผ่าน Nominatim
As a ผู้ใช้แอป, I want ให้การค้นหาสถานที่ผ่าน Nominatim ทำงานอย่างมีมารยาทตาม usage policy ของ OSM และแจ้งสถานะที่เข้าใจง่ายเมื่อค้นหาไม่ได้, so that ไม่เจอแอปค้าง/error ที่สื่อความหมายไม่ได้เมื่อเน็ตมีปัญหาหรือค้นหาบ่อยเกินไป

**Acceptance Criteria:**
- [ ] ทุก request ที่ยิงไปยัง Nominatim ต้องแนบ custom `User-Agent` header ตามที่ทีม dev กำหนด (ไม่ใช้ User-Agent default ของ HTTP client) ตาม OSM Usage Policy
- [ ] การค้นหาต้องหน่วงเวลา (debounce) หลังผู้ใช้หยุดพิมพ์อย่างน้อยระยะเวลาหนึ่งก่อนยิง request จริง และไม่ยิง request ถี่กว่า ~1 ครั้งต่อวินาที แม้ผู้ใช้พิมพ์เปลี่ยนคำค้นต่อเนื่องเร็วๆ (ป้องกันการยิง request รัวๆ เกิน rate limit ของ OSM)
- [ ] ถ้าผู้ใช้ค้นหาขณะไม่มีเน็ต หรือ request ไปยัง Nominatim ล้มเหลว/timeout ระบบแสดงข้อความแจ้งสถานะที่สื่อความหมายชัดเจน (เช่น "ค้นหาไม่ได้ในขณะนี้ ลองใหม่อีกครั้ง") แทนที่จะค้าง loading ตลอดไปหรือ error แบบ raw/technical
- [ ] ถ้าคำค้นไม่พบผลลัพธ์ใดๆ เลย ระบบแสดง empty state ที่สื่อว่า "ไม่พบสถานที่ที่ค้นหา" แทนที่จะแสดง list ว่างเปล่าดิบๆ
- [ ] การตรวจสอบว่า "มีเน็ตหรือไม่" ใช้วิธี opportunistic (ลองยิง request แล้ว catch error เมื่อไม่สำเร็จ) แบบเดียวกับที่ sync engine เดิมทำ (`src/sync/SyncContext.tsx`) ไม่ใช่ event-based network detection เนื่องจากโปรเจกต์นี้ไม่มี `@react-native-community/netinfo` ติดตั้ง
- [ ] ความล้มเหลวของการค้นหา Nominatim ต้องไม่กระทบ flow การกรอก/บันทึก entry ปกติของ US-4 เลย (ผู้ใช้ยังกรอก title เองแล้วบันทึกได้ตามปกติแม้ระบบค้นหาใช้งานไม่ได้ชั่วคราว)

### US-21: แนบรูปจาก iPhone (.HEIC/.HEIF) ได้โดยไม่พังการแสดงผล
As a ผู้ใช้แอป (โดยเฉพาะผู้ใช้ iPhone), I want แนบรูปจากแกลเลอรีของเครื่องได้ปกติไม่ว่ารูปต้นฉบับจะเป็นฟอร์แมตอะไร, so that ไม่เจอรูปที่แนบไว้กลายเป็นช่องว่าง/พังตอนเปิดดูหรือ sync ขึ้น cloud

- [ ] รูปที่แปลงแล้วแสดง thumbnail ได้ถูกต้องใน `PhotoPicker` ทันที และแสดงถูกต้องใน `EntryListItem`/หน้ารายละเอียด entry หลังบันทึก
- [ ] ถ้าการแปลงรูปล้มเหลว (exception จาก image manipulator) ระบบต้อง fallback ใช้ URI เดิมต่อได้ ไม่ throw error บล็อกผู้ใช้จากการเพิ่มรูปรูปอื่นๆ ที่เหลือ
- [ ] รูปที่ sync/อัปโหลดขึ้น Supabase Storage (bucket `trip-photos`) ต้องส่ง `contentType: 'image/jpeg'` เสมอสำหรับรูปที่ผ่านการแปลงแล้ว ไม่ใช้ content-type เดาอัตโนมัติจากนามสกุลไฟล์เดิม

### US-22: เห็นการ์ดสถานที่ท่องเที่ยวพร้อมรูปจริงจาก Wikipedia ในหน้าจังหวัด
As a ผู้ใช้แอป, I want เห็น Landmark ของจังหวัดเป็นการ์ดรูปภาพจริงพร้อมคำอธิบายสั้นและหมวดหมู่ แทนที่จะเป็นแค่รายการชื่อข้อความ, so that รู้จักสถานที่ก่อนตัดสินใจไปเยือนหรือกดเช็คอินได้ง่ายขึ้น

**Acceptance Criteria:**
- [ ] หน้า ProvinceDetailScreen ดึงข้อมูลสถานที่ท่องเที่ยวเพิ่มเติมจาก Wikipedia (ผ่านหมวดหมู่จังหวัดของ th.wikipedia.org) มาแสดงเป็นการ์ด **ควบคู่กับ** Landmark จาก local seed dataset เดิม (ไม่ทับ/ไม่ลบของเดิม)
- [ ] แต่ละการ์ดแสดงรูปภาพจริง (ดึงจาก Wikipedia thumbnail หรือ fallback ไป Wikimedia Commons ถ้าไม่มีรูปในบทความหลัก), ป้ายหมวดหมู่ (1 ใน 5: วัดและศาสนสถาน/ธรรมชาติและภูเขา/ทะเลและชายหาด/ประวัติศาสตร์และวัฒนธรรม/ช้อปปิ้งและสันทนาการ หรือ fallback "สถานที่ท่องเที่ยว" ถ้าจัดหมวดไม่ได้), และคำอธิบายสั้น (ถ้ามี)
- [ ] การ์ดที่ไม่มีรูปภาพเลย (ทั้งจาก Wikipedia และ Commons) ยังต้องแสดงผลได้โดยไม่ error/ไม่มีพื้นที่ภาพว่างเปล่าที่ดูพัง (มี placeholder ที่เหมาะสม)
- [ ] แต่ละการ์ดมีปุ่มเช็คอิน (สถานะ "+ กดเช็คอิน" / "✓ เช็คอินแล้ว") ที่ผูกกับ `CheckinContext` เดิม ใช้งานร่วมกับสถานะ Province Master (US-9) ได้เหมือน Landmark เดิมทุกประการ พร้อม accessibility role ที่สื่อว่าเป็นสวิตช์เปิด/ปิด (accessible เหมือนกับ toggle อื่นในแอป)
- [ ] ถ้าเรียก Wikipedia API ไม่สำเร็จ (ไม่มีเน็ต/timeout/error) หน้าจังหวัดยัง render ได้ปกติโดยแสดงเฉพาะ Landmark จาก local seed dataset เดิม ไม่ error ไม่ค้าง loading ตลอดไป
- [ ] จังหวัดที่ไม่มีทั้ง local seed data และ Wikipedia ไม่คืนผลลัพธ์เลย ยังคงเข้า empty state เดิมของ US-8 ("ยังไม่มีข้อมูลสถานที่แนะนำ")

### US-23: ค้นหาและกรอง Landmark ภายในหน้าจังหวัด
As a ผู้ใช้แอป, I want ค้นหาชื่อสถานที่หรือกรองตามหมวดหมู่ภายในรายการ Landmark ของจังหวัดที่กำลังดูอยู่, so that หาสถานที่ที่สนใจเจอได้เร็วขึ้นเมื่อจังหวัดนั้นมี Landmark จำนวนมาก (โดยเฉพาะหลังรวมข้อมูลจาก Wikipedia แล้ว)

**Acceptance Criteria:**
- [ ] หน้า ProvinceDetailScreen มีช่องค้นหาที่กรองรายการ Landmark **เฉพาะของจังหวัดนั้น** แบบ real-time ตามคำที่พิมพ์ (matching กับชื่อ Landmark อย่างน้อย)
- [ ] มี filter chip ตามหมวดหมู่ (5 หมวดตาม US-22 + ตัวเลือก "ทั้งหมด") ให้เลือกดูเฉพาะหมวดที่สนใจ ใช้ร่วมกับช่องค้นหาได้พร้อมกัน (AND condition)
- [ ] Progress indicator ("เช็คอินแล้ว X/Y แห่ง" จาก US-8) และแผนที่จุดพิกัด (`LandmarkMap` จาก US-18) ยังคงทำงานถูกต้องกับรายการเต็ม (ไม่ใช่แค่ผลลัพธ์ที่ถูกกรอง) — การค้นหา/กรองมีผลแค่กับรายการที่แสดงในการ์ด ไม่กระทบตัวเลข progress หรือจุดบนแผนที่
- [ ] ค้นหา/กรองแล้วไม่พบผลลัพธ์ แสดง empty state ที่สื่อความหมายชัดเจน (ไม่ใช่ list ว่างเปล่าดิบๆ) แยกจาก empty state ของ US-8 ("จังหวัดนี้ไม่มีข้อมูล Landmark เลย")

### US-24: ค้นหาจังหวัดหรือสถานที่ท่องเที่ยวทั่วประเทศจากหน้าแรก

- [ ] ค้นหาได้ทั้งชื่อจังหวัด (ทั้งภาษาไทย `nameTh` และอังกฤษ `nameEn`, ครบทั้ง 76 จังหวัด) และชื่อ Landmark ที่มีอยู่ใน local dataset ที่โหลดไว้แล้ว (`thailand-landmarks.ts`) — ไม่ต้องครอบคลุมผลลัพธ์จาก Wikipedia ที่ยังไม่เคยถูก fetch เข้ามา (ตามสมมติฐานด้านบน)
- [ ] แต่ละผลลัพธ์ในรายการแสดงสัญลักษณ์แยกประเภทชัดเจนระหว่างจังหวัด (📍) และสถานที่ (🏛️)
- [ ] แตะผลลัพธ์รายการใดก็ตาม (ทั้งจังหวัดและ Landmark) นำทางไปหน้า ProvinceDetailScreen ของจังหวัดที่เกี่ยวข้องถูกต้องตรงกับ provinceId
- [ ] การค้นหานี้ทำงานได้ offline เต็มรูปแบบ (ไม่ต้องมีเน็ต) เพราะค้นหาจาก local dataset ที่โหลดมาแล้วเท่านั้น

### US-25: แยกแยะ "จังหวัดยังไม่มีข้อมูล Landmark" ออกจาก "ดึงข้อมูลจาก Wikipedia ล้มเหลว" พร้อมทางลองใหม่ (Bug Fix)
As a ผู้ใช้แอป, I want เห็นข้อความที่บอกชัดเจนว่าทำไมหน้าจังหวัดที่กำลังดูไม่มีรายการ Landmark ให้เห็น (จังหวัดนี้ยังไม่มีข้อมูลจริงๆ หรือระบบดึงข้อมูลล้มเหลว) และมีทางสั่งให้ลองดึงข้อมูลใหม่ได้เมื่อล้มเหลว, so that ไม่เข้าใจผิดว่าแอปพังหรือจังหวัดนี้ไม่มีสถานที่ท่องเที่ยวใดๆ เลย ทั้งที่จริงบางครั้งเป็นแค่ปัญหาการดึงข้อมูลชั่วคราว

**Acceptance Criteria:**
- [ ] เมื่อจังหวัดที่กำลังดูไม่มีข้อมูลใน local seed dataset และการดึงข้อมูลจาก Wikipedia (`fetchAttractionsForProvince`) สำเร็จจริง (ไม่มี exception) แต่คืนผลลัพธ์เป็น array ว่าง (ไม่มีบทความในหมวดหมู่ของจังหวัดนั้น) หน้าจอต้องแสดง empty state เดิมตาม US-8/US-22 ("ยังไม่มีข้อมูลสถานที่แนะนำ") เหมือนเดิมทุกประการ ไม่เปลี่ยนพฤติกรรมของเคสนี้
- [ ] เมื่อการดึงข้อมูลจาก Wikipedia ล้มเหลวจริง (network error, timeout, HTTP error, หรือ parse error ที่ทำให้ `fetchAttractionsForProvince` throw/reject) หน้าจอต้องแสดง "สถานะข้อผิดพลาด" ที่แยกจาก empty state อย่างชัดเจนด้วยข้อความที่สื่อว่าดึงข้อมูลไม่สำเร็จ (เช่น "โหลดข้อมูลสถานที่ไม่สำเร็จ") — ต้องไม่ใช้ข้อความ/สถานะเดียวกับ "ยังไม่มีข้อมูลสถานที่แนะนำ"
- [ ] error state ต้องมีทางให้ผู้ใช้สั่งให้ระบบลองดึงข้อมูลจาก Wikipedia ใหม่อีกครั้งได้จากหน้าจอเดิมทันที โดยไม่ต้องออกจากหน้าจังหวัดนั้นแล้วกลับเข้ามาใหม่ (ระบุเฉพาะพฤติกรรมว่าต้องมีทางลองใหม่ได้ ไม่ระบุรูปแบบ UI ที่แน่นอน)
- [ ] ถ้าจังหวัดนั้นมี Landmark จาก local seed dataset อยู่แล้ว (curate ไว้ล่วงหน้าตาม US-8) แต่การดึงข้อมูลเสริมจาก Wikipedia ล้มเหลว รายการ Landmark จาก local seed dataset เดิมต้องยังแสดงผลได้ปกติครบถ้วนเหมือนเดิม โดย error state ของ Wikipedia แสดงแยกเป็นส่วนเสริม ไม่ทำให้ Landmark เดิมที่มีอยู่แล้วหายไปด้วย (ไม่ regress ข้อ AC ของ US-22 ที่ระบุว่า fetch ล้มเหลวต้อง fallback แสดงเฉพาะ local seed data)
- [ ] ทดสอบได้จริงโดย mock ให้ `fetchAttractionsForProvince` reject/throw แล้วต้องเห็น error state ปรากฏบนหน้าจอ (ไม่ใช่ empty state และไม่ใช่หน้าจอที่ไม่มีการเปลี่ยนแปลง/ค้าง loading ตลอดไป) และเมื่อ mock ให้ resolve เป็น array ว่างสำเร็จ ต้องเห็น empty state เดิม ไม่ใช่ error state — สองเคสนี้ต้องแยกผลการทดสอบออกจากกันได้ชัดเจน
- [ ] เมื่อผู้ใช้สั่งลองใหม่แล้วการดึงข้อมูลรอบถัดไปสำเร็จ error state เดิมต้องถูกเคลียร์ออกและแสดงผลลัพธ์ Landmark จาก Wikipedia ที่ดึงมาได้ตามปกติ (เหมือนกรณี fetch สำเร็จตั้งแต่แรกใน US-22)

### US-26: ขยาย Global Search ให้ค้นหาสถานที่ท่องเที่ยวทั่วประเทศแบบ dynamic ผ่าน Wikipedia (Bug Fix / Scope Change ของ US-24)
As a ผู้ใช้แอป, I want พิมพ์ชื่อสถานที่ท่องเที่ยวที่ไม่ได้อยู่ใน local dataset ที่ curate ไว้ล่วงหน้าแล้วยังหาเจอและกดไปหน้าจังหวัดนั้นได้, so that ไม่รู้สึกว่าค้นหาได้แค่สถานที่ยอดนิยมกลุ่มเล็กๆ ที่แอปเลือกมาให้เท่านั้น ทั้งที่ประเทศไทยมีแหล่งท่องเที่ยวมากกว่านั้นมาก

**บริบท**: US-24 (เดิม) กำหนดให้ Global Search (แถบค้นหาหน้า HomeScreen) เป็น local-dataset-only/offline ล้วนๆ (ดู AC เดิมข้อสุดท้ายของ US-24 และ Out of Scope เดิมด้านล่าง) — ผู้ใช้พบว่านี่คือสาเหตุที่ค้นหาได้ผลลัพธ์น้อยมาก จึงตัดสินใจเปลี่ยน scope ให้เปิดรับผลลัพธ์จาก Wikipedia แบบ dynamic ได้ โดยยังคง "AC เดิม" ของ US-24 ไว้ทั้งหมดสำหรับ**เฉพาะผลลัพธ์จาก local dataset**

**Acceptance Criteria:**
- [x] ผลลัพธ์จาก local dataset (จังหวัดทั้ง 76 + Landmark ที่ curate ไว้ใน `thailand-landmarks.ts`) ยังคงต้องแสดงทันทีแบบ real-time โดยไม่ต้องรอ network เหมือนเดิมทุกประการ (US-24 AC เดิมข้อ 1-4 ไม่เปลี่ยน) — ส่วนนี้ต้องพิสูจน์ได้ว่าไม่เรียก `fetch` เลย แม้แต่ตอนพิมพ์ query ที่ตรงกับ local dataset
- [x] เมื่อพิมพ์ query อย่างน้อย 2 ตัวอักษร ระบบต้อง debounce (~450ms) แล้วยิงค้นหาแบบ nationwide ผ่าน Wikipedia (`searchAttractionsGlobal`) เพิ่มเติมจากผลลัพธ์ local โดยไม่ scope การค้นหาด้วยจังหวัดปัจจุบันที่ผู้ใช้กำลังดูอยู่ (bug เดิม: การส่ง provinceNameTh ปัจจุบันเข้าไปผูกกับ query ทำให้ผลลัพธ์แคบลงมาก แม้แต่ในจังหวัดเดียวกัน)
- [x] ผลลัพธ์จาก Wikipedia ที่ไม่สามารถระบุจังหวัดเจ้าของได้ (resolve provinceId ไม่ได้จาก categories ของบทความ) ต้องไม่แสดงในรายการ เพราะไม่มีปลายทางให้กดนำทางไป
- [x] ผลลัพธ์จาก Wikipedia ที่ชื่อซ้ำกับผลลัพธ์ local ที่แสดงอยู่แล้ว (เทียบด้วยชื่อ) ต้องไม่แสดงซ้ำ
- [x] ระหว่างรอผลลัพธ์จาก Wikipedia ต้องมี loading indicator (ไม่ใช่ค้างเงียบๆ) และต้องไม่บล็อกไม่ให้เห็นผลลัพธ์ local ที่มีอยู่แล้วระหว่างรอ
- [x] แตะผลลัพธ์จาก Wikipedia ที่ resolve จังหวัดได้แล้ว ต้องนำทางไปหน้า ProvinceDetailScreen ของจังหวัดนั้นถูกต้อง เหมือนผลลัพธ์ local

**Out of Scope เพิ่มเติม**:
- การ geocode/ระบุจังหวัดด้วยวิธีอื่นนอกจากการจับคู่ชื่อจังหวัดใน categories ของบทความ Wikipedia (เช่น ไม่ใช้ coordinates/GPS จากบทความ) — ถ้า resolve ไม่ได้ ผลลัพธ์นั้นจะถูกซ่อนไปเฉยๆ ตาม AC ข้อ 3
- การ cache ผลการค้นหาแบบ persistent (เก็บใน local storage/DB) — cache เป็นแค่ระดับ in-memory ต่อ session เท่านั้น (ตาม `photoCache`/`provinceCache` เดิมใน `wikipediaService.ts`)

**หมายเหตุ**: บรรทัด Out of Scope เดิมของรอบ Landmark Check-in & Supabase Integration ที่ระบุว่า "Global search (US-24) ไม่ครอบคลุมการค้นหาสถานที่จาก Wikipedia แบบ dynamic" **ถูก supersede โดย US-26 นี้แล้ว** — ไม่ใช่ scope ที่ยังไม่ทำอีกต่อไป

### US-27: ฝัง Landmark dataset จริงจาก TAT (การท่องเที่ยวแห่งประเทศไทย) ให้ครอบคลุมเกือบทุกจังหวัดแบบ instant/offline (ต่อยอด US-26)
As a ผู้ใช้แอป, I want เปิดหน้าจังหวัดหรือค้นหาสถานที่ท่องเที่ยวแล้วเห็นข้อมูลทันทีโดยไม่ต้องรอโหลด แม้จังหวัดนั้นจะไม่เคยถูก curate ไว้ในแอปมาก่อนเลย, so that ไม่ต้องนั่งรอว่าเมื่อไหร่สถานที่ท่องเที่ยวจะขึ้น ทั้งตอนเปิดหน้าจังหวัดและตอนค้นหา

**บริบท**: ผู้ใช้พบ open data catalog ของ TAT (https://datacatalog.tat.or.th) ที่มีสถานที่ท่องเที่ยวทั่วประเทศ 8,634 รายการ ครอบคลุม 78 จังหวัด พร้อมพิกัด GPS จริงครบทุกรายการ แต่**ไม่มี field รูปภาพเลย** — ผู้ใช้ยืนยันว่ารับได้ที่จะหารูปภายหลังแบบเดิม (US-26 `resolveRealPhotoForLandmark`) ขอแค่ "รายชื่อ/รายละเอียดสถานที่" พร้อมใช้ทันทีไม่ต้องรอ fetch

**สมมติฐาน**:
- ดึงข้อมูลแบบ **build-time เท่านั้น** (สคริปต์ `scripts/extract-tat-landmarks.ts` รันมือ ไม่ผูกกับ runtime ของแอป) แล้ว merge ผลลัพธ์ที่ trim แล้วเข้า `src/data/thailand-landmarks.ts` แบบถาวร (bundled) — เหมือนรูปแบบเดิมของ US-16 OSM Overpass extraction ทุกประการ (supplement-only, ไม่แตะ id เดิม)
- **จำกัดสูงสุด 15 landmark/จังหวัด** สำหรับจังหวัดที่ดึงจาก TAT (สูงกว่า cap เดิม 5 ของ Overpass เพราะข้อมูล TAT เป็นข้อมูลที่ภาครัฐคัดสรรมาแล้ว ไม่ใช่ raw POI tag) เพื่อไม่ให้ bundle บวมเกินไป (บางจังหวัดมีมากกว่า 500 รายการในข้อมูลดิบ)
- **คงจังหวัด `chaiyaphum` และ `si-sa-ket` ให้ไม่มี landmark เลยตลอดไป** เพราะมี test เดิมหลายไฟล์ (`landmarkCheckin.test.tsx`, `landmarkMapIntegration.test.tsx`, `LandmarkList.test.tsx`, `landmarkCardsWikipediaIntegration.test.tsx`) ใช้ 2 จังหวัดนี้เป็น fixture จำลอง "จังหวัดยังไม่มีข้อมูล" (US-8 empty state) โดยเฉพาะ — เป็นการตัดสินใจเก็บไว้ ไม่ใช่ข้อจำกัดทางเทคนิค
- ไม่แก้ logic การ fetch Wikipedia เสริม (`fetchAttractionsForProvince`) ใน `LandmarkList.tsx` เลย — ยังทำงานเหมือนเดิมทุกประการ เพียงแต่ตอนนี้ผลลัพธ์เริ่มต้น (local, synchronous) มีเนื้อหาให้เห็นทันทีในเกือบทุกจังหวัดแล้ว ไม่ใช่หน้าว่างเปล่าระหว่างรอ

**Acceptance Criteria:**
- [x] 74/76 จังหวัด (ยกเว้น chaiyaphum, si-sa-ket ตามสมมติฐาน) มี landmark อย่างน้อย 1 รายการใน `src/data/thailand-landmarks.ts` แบบ bundled/offline ทันที ไม่ต้องรอ network เพื่อเห็นเนื้อหาเริ่มต้นเมื่อเปิดหน้าจังหวัด

- การเติม landmark ให้ครบ 76/76 จังหวัด (chaiyaphum, si-sa-ket ยังว่างตามสมมติฐาน)
- การ refresh ข้อมูลอัตโนมัติเมื่อ TAT อัปเดต dataset ใหม่ — เป็น snapshot ณ วันที่รันสคริปต์เท่านั้น ต้องรันสคริปต์ใหม่ด้วยมือถ้าต้องการข้อมูลล่าสุด

> **อัปเดต (รอบ 13 — bug fix จริงที่ผู้ใช้เจอ)**: ผู้ใช้ค้นหา "ชะอำ" (หาดชะอำ, เพชรบุรี) แล้วไม่เจอ แม้ยืนยันว่ามีใน dataset ที่ให้ไป ตรวจพบ 2 ปัญหา: (1) AC เดิมข้างบนจำกัดว่า "29 จังหวัดที่เพิ่มมาใหม่" เท่านั้นที่ได้ TAT data — แต่ยังมีอีก **37 จังหวัด** ที่มี OSM data บางๆ (2-5 รายการ, ไม่มี description) จาก T60/T61 อยู่แล้ว ถูกข้ามไปทั้งหมดเพราะ AC เดิมตีความ "ยังไม่ curate" แคบเกินไป (เฉพาะจังหวัดที่มี 0 รายการ) — แก้แล้วโดยเติม TAT data ให้ครบทั้ง 66 จังหวัดที่ไม่ใช่ pilot (นับรวมของเดิมไม่ให้เกิน cap 15/จังหวัด) (2) แม้จังหวัดจะได้ TAT data แล้ว "หาดชะอำ" ก็ยังไม่ติด top-15 เพราะพิสูจน์แล้วว่า**ไม่มี field ไหนใน TAT dataset ที่บ่งบอกความดังได้น่าเชื่อถือ** (ทดลองทั้ง "มี description หรือไม่" และ "ความยาว description" แล้วยังพลาด) จึงเพิ่มสถาปัตยกรรมใหม่: **แยก "search index" (`src/data/tat-search-index.ts`, ไม่ cap, 6,319 รายการ/66 จังหวัด) ออกจาก "display list" (`thailand-landmarks.ts`, cap 15/จังหวัดเหมือนเดิม)** — การค้นหา (`GlobalSearchBar.tsx`) ค้นจาก index เต็มที่ไม่ cap แต่การ์ดที่โชว์ตอนเปิดหน้าจังหวัดยังคง cap 15 เหมือนเดิมเพื่อ UX/bundle size รายละเอียดเต็มใน `docs/dev-notes.md` รอบ 13

### US-28: เปลี่ยนโครงสร้าง root navigation เป็น Bottom Tab Bar (แผนที่ / ข่าว)
As a ผู้ใช้แอป, I want สลับดูระหว่างหน้าแผนที่กับหน้าข่าวท่องเที่ยวได้ง่ายผ่านแถบแท็บด้านล่าง, so that เข้าถึงทั้งสองฟีเจอร์หลักของแอปได้สะดวกโดยไม่ต้องกดย้อนกลับไปมาหลายจังหวะ

**Acceptance Criteria:**
- [ ] root navigator ของแอป (`AppNavigator.tsx`) เปลี่ยนจาก native stack เดี่ยวเป็น Bottom Tab Navigator ที่มี 2 แท็บเสมอทุกครั้งที่เปิดแอป: "แผนที่" และ "ข่าว" (พร้อมไอคอน + label ภาษาไทย) ไม่ใช่ทางเลือกที่ซ่อนอยู่หรือเข้าถึงยาก
- [ ] แท็บ "แผนที่" แสดงเนื้อหาเดิมของ HomeScreen ทั้งหมด (แผนที่ 3D, global search bar, ปุ่มไอคอน Stats/Settings) — พฤติกรรมเดิมทุกข้อของ US-1, US-2, US-3, US-14, US-24, US-26 ต้องยังทำงานถูกต้องเหมือนก่อนเปลี่ยน navigation ไม่มี regression
- [ ] แท็บ "ข่าว" แสดง NewsScreen ใหม่ (รายละเอียดตาม US-29 ถึง US-32) เป็นหน้าจอเริ่มต้นของแท็บนั้น
- [ ] ปุ่มไอคอน Stats และ Settings ปรากฏใน header และ navigate ไปหน้า Stats/Settings เดิมได้ถูกต้องจากทั้ง 2 แท็บ (ไม่ใช่แท็บที่ 3 แยกต่างหาก) โดย push เข้า stack ที่ซ้อนอยู่ในแท็บนั้นๆ
- [ ] การแตะจังหวัด/Landmark จากแท็บ "แผนที่" ยัง push ไปหน้า ProvinceDetail/AddEntry ภายใน stack ของแท็บ "แผนที่" ได้ตามเดิม (ไม่กระทบ flow US-2/US-4) และเมื่อสลับไปแท็บ "ข่าว" แล้วกลับมาแท็บ "แผนที่" ต้องเห็นหน้าจอ/state เดิมที่ค้างอยู่ ไม่ reset กลับไปหน้าแรกของ stack
- [ ] route dev-only เดิม (`Map2DValidation`) ยังคงเข้าถึงได้ในโหมด dev เหมือนเดิม ไม่ถูกลบหรือเสียหายจากการเปลี่ยนโครงสร้าง navigation

### US-29: ดูรายการข่าวท่องเที่ยวไทยจาก RSS feed จริง
As a ผู้ใช้แอป, I want เห็นรายการข่าว/บทความเกี่ยวกับการท่องเที่ยวไทยที่กำลังอัปเดตอยู่ในแท็บข่าว, so that ติดตามข่าวสารท่องเที่ยวที่น่าสนใจได้โดยไม่ต้องออกจากแอปไปหาเอง

**Acceptance Criteria:**
- [ ] เปิดแท็บ "ข่าว" ครั้งแรก (มีเน็ต) ระบบดึงข้อมูลจาก RSS feed จริงที่กำหนด (ทีม dev ต้อง verify endpoint ตามสมมติฐานด้านบนก่อน implement) แล้ว parse เป็นรายการข่าว แสดงเรียงจากวันที่เผยแพร่ล่าสุดไปเก่าสุด (`pubDate`)
- [ ] แต่ละรายการข่าวแสดงอย่างน้อย: รูปภาพปก (หรือ placeholder ถ้าไม่มี), หัวข้อข่าว (title), สรุปสั้น (summary/description ที่ตัด HTML tag ออกแล้ว ไม่แสดง raw HTML), วันที่เผยแพร่ในรูปแบบอ่านง่าย
- [ ] รายการข่าวรองรับ pull-to-refresh เพื่อบังคับดึงข้อมูลใหม่จาก RSS ทันที โดยไม่ต้องรอรอบ cache อัตโนมัติ
- [ ] ระหว่างกำลังดึงข้อมูล RSS ครั้งแรก (ยังไม่มี cache ให้แสดง) หน้าจอแสดง loading state ที่ชัดเจน (ไม่ใช่หน้าจอว่างเปล่าเงียบๆ)
- [ ] ทดสอบได้จริงด้วย mocked RSS response (XML string) ที่ inject เข้า parser แล้วตรวจสอบว่ารายการที่ parse ได้ตรงกับจำนวน/เนื้อหาของ mock

### US-30: Caching และการทำงานแบบ Offline-Friendly ของหน้าข่าว
As a ผู้ใช้แอป, I want ยังเห็นข่าวที่เคยโหลดไว้แม้ตอนนี้ไม่มีเน็ต, so that ไม่ต้องเจอหน้าจอว่างเปล่าทุกครั้งที่เปิดแท็บข่าวโดยไม่มีสัญญาณ

**Acceptance Criteria:**
- [ ] ทุกครั้งที่ดึง RSS สำเร็จ ผลลัพธ์ (parsed news items) ถูก persist ลง local storage (เช่น AsyncStorage) พร้อม timestamp ของการดึงล่าสุด
- [ ] เปิดแท็บ "ข่าว" โดยไม่มีเน็ต (หรือ RSS request ล้มเหลว) ระบบแสดงข่าวชุดล่าสุดที่ cache ไว้ทันทีจาก local storage พร้อม indicator บอกว่าเป็นข้อมูลจาก cache (เช่น "อัปเดตล่าสุด: ...") แทนที่จะแสดงหน้าว่างเปล่า
- [ ] ถ้ายังไม่เคย fetch สำเร็จเลยสักครั้ง (cache ว่างเปล่า) และตอนนี้ไม่มีเน็ต/ดึงล้มเหลว ระบบแสดง error state ที่สื่อความหมายชัดเจน (ดู US-32) แทนที่จะ error แบบ raw หรือค้าง
- [ ] เมื่อมีเน็ตกลับมาและผู้ใช้เปิดแท็บข่าวอีกครั้งหลังผ่านช่วงเวลา cache ที่กำหนด (ตาม assumption) ระบบดึงข้อมูลใหม่อัตโนมัติในพื้นหลังโดยไม่บล็อกการแสดงผลข่าว cache เดิมระหว่างรอ (แสดงของเก่าก่อน แล้วสลับเป็นของใหม่เมื่อโหลดเสร็จ)

### US-31: เปิดอ่านข่าวเต็มที่ต้นทางผ่าน In-App Browser
As a ผู้ใช้แอป, I want กดที่ข่าวแล้วเปิดอ่านเนื้อหาเต็มจากเว็บไซต์ต้นทางโดยไม่ต้องออกจากแอป, so that อ่านรายละเอียดข่าวแบบเต็มพร้อมรูป/สื่อครบถ้วนจากผู้เผยแพร่จริง โดยยังรู้สึกอยู่ในแอปเดิม

**Acceptance Criteria:**
- [ ] แตะรายการข่าวใดๆ ในรายการ (US-29) แล้วเปิด in-app browser (`expo-web-browser` `openBrowserAsync`) ไปยัง URL ต้นทาง (`link` จาก RSS item) ทันที ไม่ใช่การแสดงเนื้อหาที่ parse/render เองในแอป (ไม่ทำ full article parsing)
- [ ] ปิด in-app browser แล้วกลับมาที่รายการข่าวเดิม โดย scroll position และสถานะรายการยังอยู่เหมือนก่อนกด (ไม่ reset กลับไปบนสุด)
- [ ] ถ้า URL ของข่าวนั้นไม่ถูกต้อง/ว่างเปล่า (parse ผิดพลาด) ระบบต้องไม่ crash แต่แสดงข้อความแจ้งว่าเปิดข่าวนี้ไม่ได้แทน
- [ ] อุปกรณ์ที่ไม่มีเน็ต ณ ตอนกดข่าว แสดงข้อความแจ้งว่าต้องมีอินเทอร์เน็ตเพื่ออ่านเนื้อหาเต็ม แทนที่จะเปิด browser ค้างเป็นหน้าขาว/error ของเบราว์เซอร์ที่ไม่สื่อความหมาย

### US-32: จัดการ Edge Case ของข้อมูลข่าว (feed ว่าง, รูปขาด, ข่าวซ้ำ, ดึงล้มเหลว)
As a ผู้ใช้แอป, I want ให้หน้าข่าวแสดงผลได้อย่างเหมาะสมแม้ข้อมูลจาก RSS ไม่สมบูรณ์หรือดึงไม่สำเร็จ, so that ไม่รู้สึกว่าแอปพังหรือข้อมูลผิดปกติเมื่อแหล่งข่าวมีปัญหา

**Acceptance Criteria:**
- [ ] ถ้า RSS feed คืนผลลัพธ์เป็นรายการว่างเปล่า (parse สำเร็จแต่ไม่มี item เลย) แสดง empty state ที่สื่อว่า "ยังไม่มีข่าวในขณะนี้" แยกจาก error state ของการดึงข้อมูลล้มเหลว
- [ ] ข่าวที่ไม่มีรูปภาพ (ไม่มี enclosure/media:content และ parse จาก description ไม่เจอรูปเลย) แสดง placeholder image ที่เหมาะสม ไม่ใช่พื้นที่ว่างเปล่า/broken image icon
- [ ] ข่าวที่มี `link` หรือ `title` ซ้ำกัน (เช่น feed ส่งรายการซ้ำมาจากหลาย category) ต้อง deduplicate ก่อนแสดงผล โดยเก็บเฉพาะรายการแรกที่เจอ (ไม่แสดงซ้ำในรายการเดียวกัน)
- [ ] เมื่อ RSS request ล้มเหลวจริง (network error, timeout, HTTP error, XML parse error) และไม่มี cache เดิมให้ fallback แสดง error state ที่มีข้อความสื่อความหมายง่าย พร้อมปุ่ม/ทางให้ลองดึงใหม่ได้ทันทีจากหน้าจอเดิม (ไม่ต้องออกจากแท็บแล้วกลับเข้ามาใหม่) — pattern เดียวกับ US-25
- [ ] ข่าวที่ไม่มี `pubDate` ที่ parse ได้ (ค่าไม่ถูกต้อง/ขาด) ยังคงแสดงในรายการโดยจัดไว้ท้ายสุด (หลังข่าวที่มีวันที่ถูกต้องทั้งหมด) แทนที่จะทำให้การเรียงลำดับทั้งหมด error/พัง

## Out of Scope
- ระบบบัญชีผู้ใช้ (login/signup), multi-user, การซิงก์ข้อมูลกับ backend/cloud
- การรองรับประเทศอื่นนอกจากไทย หรือจังหวัดบึงกาฬ (ไม่มีในชุดข้อมูลต้นทาง)
- การยืนยันตำแหน่งจริงด้วย GPS ว่าผู้ใช้ไปจังหวัดนั้นจริง (เชื่อข้อมูลที่ผู้ใช้กรอกเอง)
- การแชร์บันทึก/รูปภาพไปยังโซเชียลมีเดียหรือผู้ใช้อื่น
- การแบ่งปัน/export ข้อมูล (เช่น export เป็น PDF, backup ขึ้น cloud)
- โหมด offline/online sync conflict resolution (ไม่มี backend ตั้งแต่ต้น)
- การค้นหา/กรอง entry ด้วยคำค้นหรือแท็กแบบละเอียด (เกินกว่าการแสดงแท็กที่มีอยู่)
- การแจ้งเตือน (push notification) เพื่อชวนกลับมาบันทึกทริป
- Achievement/badge เพิ่มเติมนอกเหนือจากการปลดล็อกแผนที่และหน้าสถิติที่ระบุไว้
- การแก้ไข/ลบข้อมูล province เดิม (nameEn, nameTh, path, region, centroid) — ถือเป็นข้อมูลอ่านอย่างเดียวจาก dataset ที่ให้มา

### Out of Scope เพิ่มเติม (รอบ Landmark Check-in & Supabase Integration)
- การล็อกอินด้วย email/password หรือ social login แบบเต็มรูปแบบตั้งแต่ต้น (รอบนี้มีเฉพาะ Anonymous Auth + ปุ่มผูก email ภายหลังตาม US-11 เท่านั้น ไม่มี "สมัครสมาชิกด้วยอีเมลตั้งแต่แรก" เป็น flow หลัก)
- การเชื่อมต่อ Supabase project จริง (production credentials), การ deploy/provision Supabase infrastructure จริง — รอบนี้ทดสอบด้วย mocked/local client เท่านั้น
- การ merge ข้อมูลแบบละเอียด (field-level merge) เมื่อเกิด sync conflict — ใช้ last-write-wins ทั้ง record ตามสมมติฐานที่ระบุไว้เท่านั้น
- การกู้คืนข้อมูลของ anonymous session ที่ไม่เคยผูก email และสูญหายไปแล้ว (เช่น ลบแอปไปแล้ว) — ไม่มีกลไก recovery ใดๆ ให้ในรอบนี้ นอกจากคำเตือนล่วงหน้าตาม US-11
- การแชร์/เปรียบเทียบสถิติ Landmark check-in ระหว่างผู้ใช้หลายคน (social/leaderboard features)
- Push notification หรือการแจ้งเตือนเมื่อ sync สำเร็จ/ล้มเหลว (มีเพียง in-app status indicator ตาม US-12 เท่านั้น)

> **หมายเหตุ (อัปเดตรอบ OSM Data Integration):** ข้อความ 2 ข้อที่เคยระบุไว้ในหัวข้อนี้ — "การคัดสรร/ป้อนข้อมูล Landmark จริงให้ครบทั้ง 76 จังหวัด" และ "UI/แผนที่แสดงตำแหน่งพิกัด Landmark บนแผนที่" — ถูก **ย้ายเข้ามาอยู่ใน scope แล้ว** ตาม US-16, US-17 และ US-18 ตามลำดับ จึงถูกนำออกจากรายการ Out of Scope นี้เพื่อไม่ให้ขัดแย้งกัน ดูขอบเขตที่ยังไม่รวมของรอบนี้ในหัวข้อ "Out of Scope เพิ่มเติม (รอบ OSM Data Integration)" ด้านล่าง

### Out of Scope เพิ่มเติม (รอบ OSM Data Integration)
- Runtime fetch จาก Overpass API ทุกครั้งที่เปิดแอป — extraction เป็น one-time/build-time script เท่านั้น (US-16) แอป production ต้องไม่เรียก Overpass เลย
- การ manual QA/ตรวจสอบคุณภาพทีละแห่งโดยคนว่าแต่ละ Landmark ที่ได้จาก Overpass เป็นสถานที่ที่มีชื่อเสียง/เหมาะสมจริงหรือไม่ — เชื่อผลลัพธ์จาก filter tags ที่กำหนดเป็นหลัก ทีม content ทำ manual review เพิ่มเติมเฉพาะจังหวัดที่ข้อมูลไม่ครบ 3 แห่งเท่านั้น (นอก sprint พัฒนาโค้ด)
- แผนที่แบบ interactive เต็มรูปแบบ (เลื่อนดู/ซูม/สลับ base map) หรือการนำทาง (turn-by-turn navigation) ไปยัง Landmark — รอบนี้มีเฉพาะการแสดงตำแหน่งเป็นจุดบนแผนที่ระดับจังหวัดตาม US-18
- การคำนวณระยะทาง/เวลาเดินทางระหว่าง Landmark หรือจาก GPS ปัจจุบันของผู้ใช้
- การบันทึกผลลัพธ์จาก Nominatim ที่ผู้ใช้ค้นหาไว้เป็น Landmark ถาวรในระบบ (เช่นเสนอให้ผู้ใช้อื่นเห็น หรือเพิ่มเข้า seed dataset อัตโนมัติ) — ผลการค้นหาถูกใช้เพื่อ prefill entry ของผู้ใช้คนนั้นเท่านั้นตาม US-19
- การ cache ผลการค้นหา Nominatim ไว้ใช้ offline หรือการทำ local search index ครอบคลุมสถานที่ทั้งประเทศ — การค้นหาแบบ dynamic (US-19/US-20) ต้องใช้เน็ตเสมอ ไม่มี fallback แบบ offline
- การรองรับผู้ให้บริการค้นหาสถานที่อื่นนอกจาก OSM Nominatim (เช่น Google Places API)
- การ seed ตาราง `landmarks` ขึ้น Supabase production project จริง — รอบนี้ทดสอบผ่าน mocked/local client เท่านั้น (เช่นเดียวกับ US-12/US-13)

### Out of Scope เพิ่มเติม (รอบ Landmark Cards & Media Integration)
- การรองรับภาษาอื่นนอกจากไทย/อังกฤษในการดึงข้อมูล/ค้นหา Wikipedia (query เฉพาะ `th.wikipedia.org` เท่านั้น)
- การ cache ข้อมูล Wikipedia ข้าม session (persist ลง local storage/sqlite) — รอบนี้เป็น in-memory cache ระหว่างเปิดแอปเท่านั้น ปิดแอปแล้ว cache หาย ต้อง fetch ใหม่
- การแก้ไข/ลบ Landmark ที่มาจาก Wikipedia โดยผู้ใช้ (เช่น report ข้อมูลผิด, ซ่อนการ์ดถาวร) หรือการ moderate/verify เนื้อหาจาก Wikipedia ก่อนแสดงผล — เชื่อผลลัพธ์จาก API ตรงๆ
- การรวม Landmark จาก Wikipedia เข้าเป็นส่วนหนึ่งของ local seed dataset ถาวร (`thailand-landmarks.ts`) หรือ sync ขึ้น Supabase — Landmark จาก Wikipedia เป็น runtime-only, แสดงผล/เช็คอินได้ในเซสชันนั้นแต่ไม่ persist เข้า dataset กลาง
- ~~Global search (US-24) ไม่ครอบคลุมการค้นหาสถานที่จาก Wikipedia แบบ dynamic~~ **[Superseded by US-26]** ตอนนี้ครอบคลุมแล้ว (ดู US-26) — ยังคงไม่ครอบคลุมการค้นหาจาก Nominatim (US-19)
- การบีบอัด/ปรับขนาดรูปแบบ progressive หรือ multi-resolution สำหรับรูปที่แปลงจาก HEIC — แปลงเป็น JPEG คุณภาพคงที่ 80% เท่านั้น ไม่มี logic ปรับคุณภาพตามขนาดไฟล์ต้นฉบับ
- การรองรับฟอร์แมตภาพพิเศษอื่นนอกจาก HEIC/HEIF ที่ RN `<Image>` แสดงผลไม่ได้อยู่แล้ว (เช่น RAW, TIFF) — ขอบเขตนี้ครอบคลุมเฉพาะปัญหา HEIC/HEIF จาก iPhone ที่ระบุไว้เท่านั้น

### Out of Scope เพิ่มเติม (รอบ Bug Fix: Landmark Loading Error Visibility)
- การ curate ข้อมูล Landmark สำหรับ 68 จังหวัดที่เหลือให้ครบด้วยมือ/เพิ่มเข้า local seed dataset ถาวร (`thailand-landmarks.ts`) — ยังคงเป็นงาน content แยกต่างหากตามสมมติฐานเดิม (รอบ Landmark Check-in & Supabase Integration / US-16 / US-17) รอบนี้แก้เฉพาะกลไก error handling/visibility ของการดึงข้อมูลจาก Wikipedia ที่ล้มเหลว ไม่ใช่การเพิ่มข้อมูลให้ครบทุกจังหวัด
- การ auto-retry เบื้องหลังแบบมี backoff/จำกัดจำนวนครั้งที่ซับซ้อน — รอบนี้กำหนดเพียงว่าต้องมีทางให้ผู้ใช้สั่ง retry เองได้จากหน้าจอ ไม่ได้บังคับให้มี retry อัตโนมัติที่ทำงานเบื้องหลังโดยผู้ใช้ไม่รู้ตัว
- การแสดงรายละเอียดทางเทคนิคของข้อผิดพลาด (เช่น HTTP status code, stack trace, ชื่อ exception) ให้ผู้ใช้ปลายทางเห็นตรงๆ — ข้อความ error ที่ผู้ใช้เห็นต้องเป็นภาษาที่เข้าใจง่าย ไม่ใช่ raw error message จากระบบ
- การเปลี่ยนแหล่งข้อมูลสำรองจาก Wikipedia ไปเป็นแหล่งอื่น หรือการเพิ่มกลไก fallback หลายชั้น (เช่น ลอง API สำรองตัวที่สองถ้า Wikipedia ล้มเหลว) — รอบนี้ยังคงใช้ Wikipedia เป็นแหล่งเดียวตามเดิมของ US-22 เพียงแต่ทำให้ความล้มเหลวมองเห็นได้และลองใหม่ได้เท่านั้น

### Out of Scope เพิ่มเติม (รอบ Bottom Tab Navigation & ข่าวท่องเที่ยว RSS)
- การทำ full article parsing/rendering เนื้อหาข่าวเองในแอป (เช่น ดึง HTML เต็มมา parse ให้อ่านสวยงามแบบ reader mode) — เปิดอ่านผ่าน in-app browser ไปต้นทางเท่านั้นตาม US-31
- การกรอง/แนะนำข่าวแบบ personalized ตามจังหวัดที่ผู้ใช้ปลดล็อกหรือ landmark ที่เช็คอินแล้ว
- การแจ้งเตือน push เมื่อมีข่าวใหม่
- การคอมเมนต์/ไลค์/แชร์ข่าวภายในแอป
- การรวมข่าวจากหลาย RSS feed พร้อมกัน (รอบนี้ใช้ 1 feed หลักตามที่ระบุ ถ้าต้องการเพิ่มแหล่งอื่นเป็น scope รอบถัดไป)
- แท็บที่ 3 สำหรับ Stats/Settings — ตัดสินใจคงไว้เป็นปุ่มไอคอนใน header ของทั้ง 2 แท็บตามสมมติฐาน ไม่ทำเป็นแท็บแยก

# ส่วนเพิ่มเติม: Bug Fix รูปภาพข่าว & ยกระดับ Animation/Motion ของ UI (รอบ 14)

## บริบทของรอบนี้
ผู้ใช้รายงาน 2 ปัญหาจากการใช้งานจริง: (1) รูปภาพข่าวในแท็บ "ข่าว" ไม่ขึ้นแสดงเลยสักรายการ และ (2) รู้สึกว่าการ redesign UI/UX ที่ทำมาหลายรอบ "เหมือนเดิมตั้งแต่วันแรก" ทั้งที่เคยขอให้ redesign ใหม่หมดพร้อม animation/response ที่สวยงามและน่าใช้ขึ้น ตรวจสอบโค้ดแล้วพบสาเหตุทางเทคนิคที่ชัดเจนของทั้งสองประเด็น (ดูสมมติฐานด้านล่าง) จึงเขียน user story ใหม่ 2 เรื่องเพื่อแก้ไขให้ตรงจุด

## สมมติฐานเพิ่มเติม (รอบ Bug Fix รูปภาพข่าว & Animation/Motion Upgrade)
- สมมติฐาน: สาเหตุที่รูปภาพข่าวไม่ขึ้นเลยคือ **RSS feed ต้นทางปัจจุบัน (`https://www.tatnews.org/feed/` ตามสมมติฐานรอบ Bottom Tab Navigation) ไม่มีข้อมูลรูปภาพแนบมาในทุกรายการเลย** (ไม่มีทั้ง `<enclosure>`, `<media:content>`, และไม่มี `<img>` ฝังในเนื้อหา description) — logic การดึงรูปใน `newsRssParser.ts` เขียนไว้ครบทั้ง 3 ทางแล้ว จึงไม่ใช่บั๊กของ parser หรือ UI component (`NewsCard.tsx`) แต่เป็นข้อจำกัดของแหล่งข้อมูล (data-source limitation) การ์ดทุกใบจึงตกไปแสดง placeholder icon (📰) เสมอตามพฤติกรรมที่ US-32 กำหนดไว้ถูกต้องแล้วสำหรับกรณี "ไม่มีรูป" — แต่ในทางปฏิบัติกลายเป็น "ทุกข่าวไม่มีรูป" ซึ่งไม่ใช่ผลลัพธ์ที่ผู้ใช้ต้องการ
- สมมติฐาน: การแก้ปัญหานี้มี **2 แนวทางทางเทคนิคที่เป็นไปได้ ให้ PM และทีม Programmer เป็นผู้เลือกร่วมกัน** ไม่ใช่สิ่งที่ BA ตัดสินใจแทน:
  - **ทางเลือก (ก) เปลี่ยน/เพิ่มแหล่งข่าวสำรองที่มีรูปแนบมาจริงในตัว feed** (เช่น Bangkok Post/The Nation หรือแหล่งอื่นที่เคยพิจารณาไว้เป็น fallback ตอน US-29 แต่ไม่ได้เลือกใช้ตอนนั้นเพราะ tatnews.org ดูเหมือนมีข้อมูลพอ) — ข้อดี: ไม่เพิ่ม network call ต่อข่าว, พฤติกรรม parser เดิมยังใช้ได้; ข้อควรพิจารณา: ต้อง verify ว่าแหล่งใหม่ยัง active และมีหมวดข่าวท่องเที่ยวไทยจริงตาม pattern เดิมของสมมติฐานรอบ Bottom Tab Navigation (ต้อง log ว่าเปลี่ยนมาใช้แหล่งใด)
  - **ทางเลือก (ข) เพิ่มการ fetch หน้าบทความแต่ละข่าวเพื่อดึง Open Graph image (`<meta property="og:image">`)** มาใช้แทน placeholder — ข้อดี: ยังคงใช้ tatnews.org เดิมได้ต่อ ไม่ต้องเปลี่ยนแหล่งข่าว; ข้อควรพิจารณา: เพิ่ม network request 1 ครั้งต่อข่าวที่แสดงในรายการ มีผลต่อ performance และความเสี่ยงเรื่อง rate-limit/เวลาโหลดที่ทีม dev ต้องออกแบบ (เช่น fetch แบบ lazy เฉพาะรายการที่มองเห็นบนจอ, cache ผลลัพธ์)
  - ทั้งสองทางเลือกยังคง**ต้องรักษาพฤติกรรม placeholder เดิมของ US-32 ไว้สำหรับข่าวที่ไม่มีรูปจริงๆ แม้หลังแก้แล้ว** (เช่นบทความที่ไม่มี og:image ในทางเลือก ข หรือแหล่งใหม่บางรายการยังไม่มีรูปในทางเลือก ก)
- สมมติฐาน: ปัญหาข้อ (2) ที่ผู้ใช้รู้สึกว่า "UI เหมือนเดิมตั้งแต่วันแรก" **ไม่ได้แปลว่าไม่มีการเปลี่ยนแปลงเกิดขึ้นจริงในโค้ด** — ตรวจสอบแล้วพบว่ามีการปรับปรุงหลายรอบ (Bento/Magazine card layout, 8pt grid, shadow, PressableScale bounce, haptic feedback, shimmer skeleton ตาม `.claude/skills/advanced-mobile-uiux/SKILL.md`) แต่การเปลี่ยนแปลงเหล่านั้นอยู่ใน**ระดับ micro-detail** (เงา, ขอบมน, bounce เบาๆ ตอนกดปุ่ม) ไม่มี **hero-level motion** ที่ผู้ใช้ทั่วไปจะสังเกตเห็นว่า "ต่างชัดเจน" เช่น ไม่มี screen transition animation ระหว่างเปลี่ยนหน้า, ไม่มี entrance animation ของ list/card ตอนข้อมูลโหลดเสร็จ, โครงสร้าง layout หลักของแต่ละหน้ายังเหมือนเดิมทั้งหมด — รอบนี้จึงมุ่งเพิ่ม motion ระดับที่สังเกตเห็นได้ชัดขึ้น โดยไม่แตะโครงสร้าง/สี/ข้อมูลเดิม
- สมมติฐาน: มีความเป็นไปได้แยกต่างหากที่ผู้ใช้กำลังดูแอปจาก **build/cache เก่าที่ยังไม่รวมการเปลี่ยนแปลงล่าสุด** (เช่น Metro bundler cache ค้าง, reload แอปไม่หมด) — นี่ไม่ใช่ประเด็นที่แก้ได้ด้วย requirement/โค้ดในรอบนี้ จึงไม่ถูกทำเป็น user story แต่ระบุไว้เป็นข้อสังเกตท้ายเอกสารส่วนนี้ให้ orchestrator แจ้งผู้ใช้แยกต่างหาก

## User Stories (ต่อ)

### US-33: แก้ปัญหารูปภาพข่าวไม่แสดงในแท็บข่าว
As a ผู้ใช้แอป, I want เห็นรูปภาพจริงประกอบข่าวในรายการข่าวเมื่อข่าวนั้นมีรูปอยู่จริงจากแหล่งข้อมูล, so that รับรู้เนื้อหาข่าวได้เร็วและน่าติดตามกว่าการเห็นแต่ไอคอน placeholder ทุกรายการเหมือนที่เป็นอยู่ตอนนี้

**Acceptance Criteria:**
- [ ] เมื่อข่าวรายการใดมีรูปภาพจริงที่สามารถดึงได้ (ไม่ว่าจะมาจาก `<enclosure>`/`<media:content>`/`<img>` ในเนื้อหาของแหล่งข่าวที่เลือกใช้ตามทางเลือก (ก) หรือจาก Open Graph image ที่ fetch เพิ่มตามทางเลือก (ข) ตามที่ PM/Programmer ตัดสินใจ) การ์ดข่าวนั้นต้องแสดงรูปจริงนั้น **ไม่ใช่ placeholder icon เสมอเหมือนปัจจุบัน**
- [ ] วัดผลได้ชัดเจนว่า **สัดส่วนข่าวที่มีรูปจริงแสดงผลต้องมากกว่า 0% อย่างมีนัยสำคัญ** เทียบกับพฤติกรรมปัจจุบันที่ทุกรายการ (100%) ตกไปแสดง placeholder — ทีม dev ต้องรายงานตัวเลขจริงหลัง implement (เช่น "X/Y ข่าวล่าสุดมีรูปแสดงผล") เป็นส่วนหนึ่งของหลักฐานทดสอบ ไม่ใช่แค่บอกว่า "แก้แล้ว"
- [ ] ข่าวที่ยังไม่มีรูปจริงให้ดึงได้จริงๆ (เช่นแหล่งข่าวนั้นไม่มีรูปในบทความนั้นเลย หรือ og:image fetch ไม่สำเร็จ) ยังคงแสดง placeholder ที่เหมาะสมตามพฤติกรรมเดิมของ US-32 ไม่ error ไม่ใช่พื้นที่ว่างเปล่า/broken image
- [ ] ถ้าเลือกใช้ทางเลือก (ข) (fetch Open Graph image เพิ่มต่อบทความ) การ fetch เพิ่มนี้ต้องไม่บล็อกการแสดงผลรายการข่าวหลัก (title/summary/date ต้องขึ้นทันทีตาม US-29 ก่อนอยู่แล้ว) และความล้มเหลวของการ fetch og:image ของข่าวรายการหนึ่งต้องไม่กระทบการแสดงผลของข่าวรายการอื่น
- [ ] ถ้าเลือกใช้ทางเลือก (ก) (เปลี่ยน/เพิ่มแหล่งข่าว) ต้อง verify ว่าแหล่งใหม่เป็น public RSS จริงที่ active และมีหมวดข่าวท่องเที่ยวไทยตามสมมติฐานเดิมของรอบ Bottom Tab Navigation และต้องปรับ/ทดสอบ `newsRssParser.ts` ให้ parse ข้อมูลจากแหล่งใหม่ได้ถูกต้องครบทุก field เดิม (title, summary, image, link, pubDate) ไม่ใช่แค่ field รูปภาพ
- [ ] ทดสอบได้จริงด้วย mocked RSS/HTML response ที่มีรูปภาพแนบอยู่จริง (ตามทางเลือกที่เลือกใช้) แล้วตรวจสอบว่าการ์ดที่ render ออกมาแสดง URL รูปที่ถูกต้องตรงกับ mock ไม่ใช่ placeholder

### US-34: ยกระดับ Animation และ Interaction Feedback ของแอปให้รู้สึกต่างชัดเจน
As a ผู้ใช้แอป, I want รู้สึกถึงความลื่นไหลและมีชีวิตชีวาของแอปอย่างชัดเจนเมื่อเปลี่ยนหน้าจอ เลื่อนดูรายการ หรือกดปุ่ม/การ์ดต่างๆ, so that รู้สึกว่าแอปได้รับการ redesign ใหม่จริง ไม่ใช่แค่หน้าตาเดิมที่มีรายละเอียดเล็กๆ น้อยๆ เปลี่ยนไป

**Acceptance Criteria:**
- [ ] มี **screen transition animation ที่มองเห็นได้ชัดเจน** ระหว่างเปลี่ยนหน้าจอหลัก (อย่างน้อยครอบคลุม: สลับแท็บ "แผนที่"/"ข่าว", เปิดหน้า ProvinceDetailScreen จาก HomeScreen, เปิดหน้า AddEntryScreen) แทนการสลับหน้าแบบทันที/default ของ navigation library โดยไม่มี custom transition (รูปแบบ animation ที่แน่นอน เช่น slide/fade/shared-element เป็นหน้าที่ของทีม UIUX/Programmer ออกแบบต่อ — requirement นี้กำหนดเฉพาะว่าต้องมี motion ที่สังเกตเห็นได้ระหว่างการเปลี่ยนหน้า)
- [ ] รายการ (list) หลักที่มีเนื้อหาหลายรายการ (อย่างน้อย: รายการ Landmark ในหน้าจังหวัด, รายการข่าวในแท็บข่าว, รายการ entry ในหน้าสถิติ) ต้องมี **entrance animation ตอนข้อมูลโหลดเสร็จและ render ครั้งแรก** (เช่น fade-in/slide-in ทีละรายการหรือเป็นกลุ่ม) แทนที่จะปรากฏขึ้นทันทีทั้งหมดพร้อมกันแบบไม่มี transition ใดๆ เหมือนปัจจุบัน
- [ ] ปุ่ม/การ์ดที่เป็น interactive element สำคัญ (เช่น ปุ่มเช็คอิน, การ์ด Landmark, การ์ดข่าว, ปุ่ม "+ เพิ่มบันทึกใหม่") ต้องมี **visual feedback ตอนกดที่มองเห็นได้ชัดเจนกว่าที่มีอยู่ในปัจจุบัน** (ทีม dev ปัจจุบันมี PressableScale bounce เบาๆ อยู่แล้ว — รอบนี้ต้องปรับให้ผู้ทดสอบทั่วไปที่ไม่ใช่ทีมพัฒนารู้สึกได้ถึงความแตกต่างอย่างชัดเจนเมื่อเทียบกับก่อนแก้ ไม่ใช่แค่ปรับค่าตัวเลข scale เล็กน้อยจนสังเกตไม่ออก)
- [ ] การเปลี่ยนแปลงทั้งหมดในรอบนี้ **ต้องไม่ทำให้ functional behavior เดิมของ user story ก่อนหน้าทั้งหมด (US-1 ถึง US-32) เปลี่ยนไป** — เช่น ข้อมูลที่แสดง, การนำทาง, ผลลัพธ์ของการกดปุ่ม ต้องเหมือนเดิมทุกประการ มีแค่ "การเคลื่อนไหวระหว่างเกิดเหตุการณ์" ที่เปลี่ยนไป
- [ ] Animation ที่เพิ่มเข้ามาต้องไม่ทำให้แอปรู้สึกหน่วง/ค้าง (เช่น สามารถกดข้ามหรือ interrupt ระหว่าง animation กำลังเล่นได้ ไม่บังคับให้ผู้ใช้รอ animation จบก่อนถึงจะกดปุ่มถัดไปได้)
- [ ] ทดสอบได้จริงอย่างน้อยในระดับที่ตรวจสอบว่า animation component/prop ที่เกี่ยวข้อง (เช่น `Animated`/`Reanimated` config, transition config ของ navigator) ถูกเพิ่ม/เปลี่ยนแปลงจริงในโค้ดของแต่ละหน้าจอที่ระบุไว้ข้างต้น ไม่ใช่แค่คงค่า default เดิมไว้

## Out of Scope เพิ่มเติม (รอบ Bug Fix รูปภาพข่าว & Animation/Motion Upgrade)
- การเปลี่ยน information architecture, สี (color palette), หรือโครงสร้างข้อมูล (data model/schema) เดิมของแอป — ผู้ใช้ขอเฉพาะ animation/response ที่สวยงามและน่าใช้ขึ้นเท่านั้น ไม่ได้ขอให้ออกแบบหน้าจอใหม่ทั้งหมดหรือเปลี่ยนสิ่งที่ผู้ใช้คุ้นเคยอยู่แล้ว
- การตัดสินใจเลือกระหว่างทางเลือก (ก)/(ข) ของ US-33 ด้วยตัวเอง — เป็นการตัดสินใจของ PM ร่วมกับทีม Programmer โดยพิจารณา trade-off ด้าน performance/ความเสถียรของแหล่งข้อมูล ไม่ใช่หน้าที่ของ BA
- การทำ full-screen shared-element transition ที่ซับซ้อน (เช่น รูปภาพขยายจากการ์ดไปเต็มจอแบบไร้รอยต่อ) หากทีม UIUX/Programmer ประเมินว่าเกินขอบเขตเวลาของรอบนี้ — ขั้นต่ำที่ต้องมีคือ screen transition ที่สังเกตเห็นได้ตาม AC ของ US-34 เท่านั้น รูปแบบที่ซับซ้อนกว่านั้นเป็นทางเลือกเสริมนอกเหนือจากที่ requirement นี้บังคับ
- การเปลี่ยนรูปแบบ/ไลบรารี animation หลักที่ใช้อยู่ในโปรเจกต์ (เช่นเปลี่ยนจาก React Native `Animated` ไปเป็นไลบรารีอื่นทั้งหมด) หากไลบรารีเดิมสามารถรองรับ AC ที่กำหนดได้อยู่แล้ว — เป็นการตัดสินใจทางเทคนิคของทีม Programmer
- การปรับปรุงรูปภาพข่าวให้มีคุณภาพ/ความละเอียดสูงขึ้น หรือการ cache รูปภาพข่าวแบบ persistent ข้าม session — อยู่นอกขอบเขตของการแก้ปัญหา "รูปไม่แสดงเลย" ในรอบนี้

## หมายเหตุท้ายเอกสาร (ไม่ใช่ user story)
> ถ้าหลังจากทีมพัฒนาทำ US-33 และ US-34 เสร็จสมบูรณ์ตาม Acceptance Criteria ทั้งหมดแล้ว ผู้ใช้ยังคงรู้สึกว่าไม่เห็นการเปลี่ยนแปลงใดๆ เลย ให้ orchestrator ตรวจสอบกับผู้ใช้ก่อนว่ากำลังเปิดดูแอปจาก **build/bundle ที่ตรงกับโค้ดล่าสุดจริงหรือไม่** (เช่น Metro bundler cache ค้างเก่า, ต้อง reload/restart Metro ด้วย cache clear, หรือเปิดแอปจาก build เก่าที่ยังไม่ได้ install ใหม่) เนื่องจากมีความเป็นไปได้ว่าปัญหาที่ผู้ใช้เห็นไม่ได้เกิดจากโค้ด/requirement แต่เกิดจากสภาพแวดล้อมการรันแอปที่ผู้ใช้ใช้ทดสอบอยู่ ณ ขณะนั้น — นี่ไม่ใช่ข้อสรุปที่ควรใช้แทนการแก้ไขจริงตาม US-33/US-34 แต่เป็นขั้นตอนตรวจสอบเพิ่มเติมที่ควรทำคู่กันก่อนสรุปว่า requirement รอบนี้ยังไม่เพียงพอ

# ส่วนเพิ่มเติม: Color Palette & Layout Redesign ทั้งแอป (รอบ 15)

## บริบทของรอบนี้
US-34 (รอบก่อน) แก้เฉพาะ animation/interaction feedback ตามที่ Out of Scope ของรอบนั้นระบุไว้ชัดเจนว่า **"ไม่เปลี่ยน color palette หรือโครงสร้าง layout เดิม"** ผู้ใช้เปิดแอปจริงแล้วยังรู้สึกว่า "เหมือนเดิมหมด" โดยเฉพาะ **HomeScreen/Map3D (หน้าแรกสุดที่เห็นทุกครั้งที่เปิดแอป) ซึ่งแทบไม่เคยถูกปรับสี/layout เลยตั้งแต่ต้นโปรเจกต์** ในขณะที่บางหน้า (LandmarkCard, StatsScreen, SettingsScreen) เคยได้รับการปรับ Bento-card/gradient ไปแล้วบางส่วนในรอบ v2-v4 (นอก pipeline requirement อย่างเป็นทางการ) ผู้ใช้ยืนยันชัดเจนแล้วว่าต้องการให้ทำรอบใหม่จริงจังเพื่อ **เปลี่ยนสี (color palette) และ layout ของแอปทั้งหมด** ให้ดู advance ขึ้นจริง ไม่ใช่แค่ animation อีกต่อไป

## สมมติฐานเพิ่มเติม (รอบ Color Palette & Layout Redesign)
- สมมติฐาน: design token ปัจจุบันทั้งหมดอยู่รวมศูนย์ที่ `src/theme.ts` (`COLORS`, `SPACING`, `RADIUS`, `SHADOWS`, `CATEGORY_COLORS`) แล้ว การ redesign รอบนี้จึงทำได้โดย**แก้ไฟล์นี้เป็นจุดเดียว**เป็นหลัก แล้วไล่ปรับแต่ละหน้าจอ/component ให้ใช้ token ที่ปรับแล้วให้ตรงกัน แทนที่จะไปแก้ hex code กระจายอยู่ทีละไฟล์
- สมมติฐาน: ความหมายเชิงสถานะ (semantic) ของสีปัจจุบันที่ผู้ใช้คุ้นเคยแล้ว — เขียว = unlocked/สำเร็จ, เทา = locked, เหลือง/ทอง = warning/Province Master badge, แดง = danger — **ยังต้องคงไว้เป็นแนวคิดเดิม** แม้ค่า hex จริงจะเปลี่ยนไปตามโทนใหม่ที่เลือก เพื่อไม่ให้ผู้ใช้ต้องเรียนรู้ความหมายของสีใหม่ทั้งหมดพร้อมกับการเปลี่ยนโทน (จะสร้างความสับสนเกินจำเป็น)
- สมมติฐาน: **ต้องข้ามการเลือกโทนสีหลักที่เจาะจง (hex code จริง) — เป็นการตัดสินใจของทีม UIUX ไม่ใช่ของ BA** ดังนั้น requirement รอบนี้เขียนเป็น "เกณฑ์ที่ผลลัพธ์ต้องผ่าน" (contrast, ความสอดคล้อง, ความแตกต่างจากเดิม) ไม่ใช่ "ต้องใช้สีนี้" — ดูหัวข้อ "จุดที่ต้องให้ PM/UIUX ตัดสินใจ" ด้านล่าง
- สมมติฐาน: การ "ปรับ layout" ในรอบนี้หมายถึงการจัดวางองค์ประกอบ (spacing, hierarchy, การจัดกลุ่มเนื้อหา, ความลึก/เงาของภาพ 3 มิติ) ให้ใช้ SPACING/RADIUS/SHADOWS token ของแอปอย่างสม่ำเสมอ **ไม่ใช่การเปลี่ยน information architecture** (เช่น ไม่ย้าย/ลบ/เพิ่มฟีเจอร์ ไม่เปลี่ยนลำดับหน้าจอ ไม่เปลี่ยนจำนวน field ในฟอร์ม) ตามที่ระบุใน Out of Scope ด้านล่าง

## จุดที่ต้องให้ PM/UIUX ตัดสินใจก่อนเริ่ม Implement (Decision Gate — ไม่ใช่สิ่งที่ BA ตัดสินใจแทน)
1. **เลือกทิศทาง color palette**: (A) ปรับปรุง (evolve) จากโทนเขียวเดิม (#1D9E75/#0F6E56) ให้มีมิติ/ความเข้ม/ความหรูขึ้น โดยยังอยู่ในตระกูลสีเขียวเดิม หรือ (B) เปลี่ยนโทนสีหลักใหม่ทั้งหมด (เช่นเปลี่ยนไปโทนอื่นที่ทีม UIUX เสนอ) — ทั้งสองทางเลือกต้องเสนอมาพร้อม mockup/ตัวอย่างให้ผู้ใช้ยืนยันก่อนเริ่มลงมือแก้โค้ดทุกหน้าจอ เพราะมีผลกับทุกหน้าจอพร้อมกัน (ถ้าทำแล้วผู้ใช้ไม่ชอบ ต้องรื้อทั้งหมดใหม่)
2. **ลำดับความสำคัญของการ implement**: จะทำทุกหน้าพร้อมกันในรอบเดียว หรือแบ่งเฟส (เช่น เริ่มจาก HomeScreen/Map3D ก่อนเพราะเป็นจุดที่ผู้ใช้บ่นตรงที่สุด แล้วตามด้วยหน้าอื่น) — มีผลต่อการวางแผน sprint ของทีม Programmer
3. **ระดับความลึกของการปรับ Map3D**: ปรับแค่สีของตึก/พื้น/แสงเงาบนโมเดล 3 มิติเดิม หรือปรับโครงสร้าง geometry/สไตล์การเรนเดอร์ตึกด้วย (ผลกระทบด้าน effort ทางเทคนิคต่างกันมาก ต้องให้ทีม Programmer ประเมินร่วมกับ UIUX)

## User Stories (ต่อ)

### US-35: กำหนดทิศทาง Color Palette ใหม่ทั้งระบบผ่าน Design Token เดียว
As a ผู้ใช้แอป, I want ให้แอปมีโทนสีใหม่ที่ดูทันสมัย/advance ขึ้นอย่างสอดคล้องกันทุกหน้าจอ ไม่ใช่สีเขียวเรียบๆ แบบเดิมที่ใช้มาตั้งแต่ต้น, so that รู้สึกว่าแอปได้รับการยกระดับจริงตั้งแต่แรกเห็น ไม่ใช่แค่ภาพเคลื่อนไหวที่เพิ่มเข้ามา

**Acceptance Criteria:**
- [ ] มีข้อสรุปจาก PM/UIUX ระบุชัดเจนว่าเลือกทิศทาง (A) หรือ (B) ตามหัวข้อ "จุดที่ต้องให้ PM/UIUX ตัดสินใจ" ข้อ 1 พร้อมตัวอย่าง/mockup ที่ผู้ใช้ยืนยันแล้ว **ก่อน**เริ่มแก้โค้ดหน้าจอใดๆ ในรอบนี้ (เป็น decision gate ที่บล็อกงานถัดไป)
- [ ] ค่าสีใหม่ทั้งหมดถูกปรับปรุงลงใน `src/theme.ts` เป็นจุดเดียว (`COLORS`, และ `CATEGORY_COLORS`/`SHADOWS` ถ้าจำเป็นต้องปรับตามโทนใหม่) ไม่มีการ hardcode ค่าสีใหม่กระจายอยู่ในแต่ละ component/screen แยกจาก token กลาง
- [ ] คู่สีที่ใช้แสดงข้อความสำคัญ (เช่น `textPrimary` บน `background`, สีตัวอักษรบนปุ่ม CTA หลัก) ต้องผ่านเกณฑ์ contrast ratio ขั้นต่ำตาม WCAG AA (อย่างน้อย 4.5:1 สำหรับข้อความขนาดปกติ) ตรวจสอบได้จริงด้วยเครื่องมือคำนวณ contrast
- [ ] ความหมายเชิงสถานะของสีที่ผู้ใช้คุ้นเคย (เขียว/โทนหลัก = unlocked, เทา = locked, เหลือง/ทอง = warning/Province Master, แดง = danger) ยังคงสื่อความหมายเดิมได้ แม้ hex code จริงจะเปลี่ยนไปตามโทนใหม่ที่เลือก
- [ ] เปรียบเทียบ before/after ของค่า token ใน `src/theme.ts` ต้องแสดงให้เห็นความแตกต่างที่จับต้องได้จริง (ไม่ใช่ปรับ hex เพียงเล็กน้อยจนแทบมองไม่เห็นความต่าง เช่นเปลี่ยนแค่ 1-2 หน่วยความสว่าง)

### US-36: Redesign หน้า HomeScreen (แผนที่ 3 มิติ, Header Progress, Legend, แถบค้นหา)
As a ผู้ใช้แอป, I want เห็นหน้าแรกของแอป (แผนที่ 3 มิติ 76 จังหวัด พร้อมส่วนหัวความคืบหน้า, legend และแถบค้นหา) มีสี/การจัดวางที่ดู advance ขึ้นอย่างชัดเจน, so that รู้สึกได้ทันทีตั้งแต่เปิดแอปครั้งแรกว่าแอปนี้ได้รับการปรับปรุงจริง ไม่ใช่แค่หน้าจอย่อยที่ไม่ค่อยได้ใช้

**Acceptance Criteria:**

## Out of Scope เพิ่มเติม (รอบ Color Palette & Layout Redesign)
- การเปลี่ยน business logic, data model/schema, หรือกติกาการปลดล็อกจังหวัด/เช็คอิน Landmark ที่มีอยู่เดิม — รอบนี้เป็นงานด้าน visual (สี/การจัดวาง) เท่านั้น ไม่แตะ logic ใดๆ ที่เคยผ่าน QA มาแล้ว
- การรื้อ/เปลี่ยนพฤติกรรม animation ที่ผ่าน QA แล้วใน US-34 — สามารถปรับ "สี" ของ element ที่มี animation อยู่ได้ตามโทนใหม่ แต่ต้องคงจังหวะ/รูปแบบการเคลื่อนไหวเดิมไว้ ไม่ใช่การออกแบบ motion ใหม่ในรอบนี้
- การเปลี่ยนโครงสร้าง navigation (จำนวนแท็บ, ลำดับหน้าจอ, route/flow การนำทาง) ที่มีอยู่ตาม US-28 — รอบนี้ไม่แตะโครงสร้างการนำทาง มีเพียงหน้าตา/สีของแต่ละหน้าจอที่เปลี่ยน
- การเปลี่ยน information architecture ในระดับ "ฟีเจอร์ที่มี/ไม่มี" ของแต่ละหน้าจอ (เช่น ไม่เพิ่ม/ลด field ในฟอร์ม, ไม่เพิ่ม/ลดปุ่มหรือส่วนเนื้อหาใหม่ที่ไม่เคยมี) — ขอบเขตจำกัดเฉพาะสี/การจัดวางองค์ประกอบที่มีอยู่แล้วเท่านั้น
- การเลือก hex code สีเฉพาะเจาะจงของโทนใหม่ด้วยตัวเอง — เป็นหน้าที่ของทีม UIUX นำเสนอและ PM/ผู้ใช้ตัดสินใจตามหัวข้อ "จุดที่ต้องให้ PM/UIUX ตัดสินใจ" ข้างต้น ไม่ใช่สิ่งที่ BA กำหนดไว้ล่วงหน้าในเอกสารนี้
- การเปลี่ยนโมเดล/geometry ของแผนที่ 3 มิติในระดับโครงสร้าง (เช่น เปลี่ยนรูปทรงบล็อกจังหวัดทั้งหมด, เปลี่ยนมุมกล้อง/perspective) เว้นแต่ PM/UIUX/Programmer จะตัดสินใจร่วมกันว่าจำเป็นตามข้อ 3 ของ Decision Gate ด้านบน — ค่าเริ่มต้นของรอบนี้คือปรับสี/แสงเงา/gradient บนโครงสร้างเดิม
